## 1. The gap and what was added

The catalog row

```
LN-L1-001  L1 / foundations
The funding output is P2WSH over the 2-of-2 funding witness script.
leanTarget := "LnLean.Bitcoin.fundingScriptPubKey"
status := .statementOnly
```

targets a **definition**, not a theorem. `LnLean.Bitcoin.fundingScriptPubKey`
only wraps a caller-supplied 32-byte program:

```lean
def fundingScriptPubKey (witnessScriptHash : ByteArray) : Script :=
  p2wsh witnessScriptHash
```

`FundingParams.witnessScriptHash` is a free field; `FundingParams.WellFormed`
checks its length but not the equation
`witnessScriptHash = SHA256(witnessScript.bytes)`.  Prior modules (`D01`,
`D41`, `F01`, `PhaseC2/FundingBridge`) already prove the byte decomposition
and a conditional binding, but their reverse direction uses **global**
injectivity `∀ a b, sha256 a = sha256 b → a = b`.  Combined with a 32-byte
output width that hypothesis is uninhabited, so those reverse bindings are
vacuous for any real SHA-256 and cannot be promoted as faithful targets.

`LnLean/Proofs/Bitcoin/FundingScriptTargets.lean` adds:

1. **Unconditional structural content.**  The seam script is the BIP 141 P2WSH
   wrapper `OP_0 <0x20> <program>`; it is 34 bytes for a 32-byte program; the
   wrapper is injective, so the output determines its program; and
   `FundingParams.witnessScript` is exactly the BOLT 3
   `OP_2 <pk1> <pk2> OP_2 OP_CHECKMULTISIG` template over the two funding keys
   in one of the two lexicographic orders.
2. **Exact hash-commitment theorem.**  Under the explicit missing invariant
   `FundingScriptHashLinked H p` (`p.witnessScriptHash = H p.witnessScript.bytes`),
   the funding `scriptPubKey` is literally
   `p2wsh (H (TwoOfTwoScriptBytes ...))` (either key order), at the
   `FundingParams`, `FundingOutput`, and confirmed-`TxOut` levels.  The
   committed *hash* is also identified with `H` of the exact 2-of-2 bytes.
3. **A non-vacuous reverse direction.**  A revealed script whose hash is the
   committed P2WSH program is the funding witness script under a finite
   **pair-level C1 admission** `CollisionFreeOn H revealed p.witnessScript.bytes`
   (`H x = H y → x = y`).  This is the P2WSH analogue of the finite-execution
   C8 HMAC contract.
4. **Mechanized assumption boundaries.**  `c1_32_does_not_bind_funding_witnessScripts`
   proves that the model's C1 (injectivity on **32-byte** preimages) does not
   bind **71-byte** funding scripts: there is a 32-byte-output hash satisfying
   C1 that collides on two distinct 71-byte strings.  Exact injectivity on all
   71-byte strings is also not assumed, because it is impossible with a
   32-byte output by pigeonhole and would make the binding vacuous.
   `fundingScriptPair_assumptions_satisfiable` proves the conditional bundle
   is satisfiable with two *distinct* well-formed funding witness scripts.
5. **C2 scope.**  C2 (HASH160 collision resistance) is not consumed by this
   target.  P2WSH commits with SHA-256; HASH160 belongs to P2WPKH outputs such
   as `to_remote`.  `Hash160CollisionResistant` is recorded only to make the
   boundary explicit.

### 2.7 Assumption-boundary theorems

```lean
abbrev CollisionResistantOn (H : ByteArray → ByteArray) (n : Nat) : Prop :=
  ∀ x y : ByteArray, x.size = n → y.size = n → H x = H y → x = y

theorem collisionResistant_iff_collisionResistantOn_32
    (H : ByteArray → ByteArray) :
    LnLean.Crypto.CollisionResistant H ↔ CollisionResistantOn H 32

abbrev Hash160CollisionResistant (H160 : ByteArray → ByteArray) : Prop :=
  ∀ x y : ByteArray, H160 x = H160 y → x = y
-- recorded for C2 scope only; no theorem in this module consumes it

theorem c1_32_does_not_bind_funding_witnessScripts :
    ∃ H : ByteArray → ByteArray,
      (∀ b : ByteArray, (H b).size = 32) ∧
      LnLean.Crypto.CollisionResistant H ∧
      ∃ x y : ByteArray,
        x.size = 71 ∧ y.size = 71 ∧ x ≠ y ∧ H x = H y

theorem fundingScriptPair_assumptions_satisfiable :
    ∃ (H : ByteArray → ByteArray) (p q : FundingParams),
      (∀ b : ByteArray, (H b).size = 32) ∧
      p.WellFormed ∧ q.WellFormed ∧
      FundingScriptHashLinked H p ∧ FundingScriptHashLinked H q ∧
      p.witnessScript.bytes ≠ q.witnessScript.bytes ∧
      CollisionFreeOn H p.witnessScript.bytes q.witnessScript.bytes
```

`fundingScriptPair_assumptions_satisfiable` uses all-zero/one 33-byte byte
strings as funding keys.  `PubKey.Valid` in this model is *length only*, so
these are model-level well-formed records, not real secp256k1 keys.  The
theorem is a logical non-vacuity witness, not a claim that `demoHash` is
SHA-256.

## 3. Assumption accounting (C1 / C2)

| Assumption | Used? | Exact role in this module |
|---|---|---|
| C1 SHA-256 collision resistance on **32-byte** preimages | **No, not directly** | `c1_32_does_not_bind_funding_witnessScripts` proves it does not bind the 71-byte witness script. The reverse direction instead takes the finite pair admission `CollisionFreeOn H revealed witnessScript`. |
| C1 exact injectivity on all **71-byte** strings | **No** | With a 32-byte output it is impossible by pigeonhole (256^71 inputs vs 256^32 outputs); assuming it would make the binding vacuous. This is why the pair form is used. |
| C2 HASH160 collision resistance | **No** | P2WSH commits with SHA-256, not HASH160. `Hash160CollisionResistant` is only a scope marker. |
| SHA-256 structural width `(M.sha256 b).size = 32` | Not needed for the structural/hash-link theorem | The hash is an arbitrary `H : ByteArray → ByteArray`; the link equation supplies the identity. Instantiating `H := M.sha256` gives the SHA-256 form. |
| `FundingScriptHashLinked H p` | **Yes, explicit hypothesis** | The missing model/construction invariant `p.witnessScriptHash = H p.witnessScript.bytes`. `WellFormed` does not imply it (D41/F01 counterexamples). |
| `FundingParams.WellFormed` | Only for the 71-byte/2-of-2-length corollary; not for the output-shape theorem | Supplies 33-byte keys and a 32-byte stored hash. |

No theorem in this module uses a global hash-injectivity hypothesis.  The only
cryptographic-style hypothesis is the finite pair admission, and
`fundingScriptPair_assumptions_satisfiable` shows it is satisfiable together
with the hash link and a 32-byte output.

## 6. Blockers and exact missing bridge

1. **Hash-link invariant is not a model field.**  `FundingParams` has
   `witnessScriptHash : ByteArray` and `WellFormed` only checks
   `size = 32`.  The equation
   `witnessScriptHash = H(witnessScript.bytes)` must be established by the
   channel-construction code (`make_funding_redeemscript` followed by SHA-256
   in rust-lightning) or added as a structure invariant.  This lane may not
   edit `LnLean/Bitcoin/Funding.lean` or `Seam.lean`, so it is an explicit
   hypothesis.
2. **No concrete SHA-256 and no computational collision-resistance game.**
   `PrimitiveModel.sha256` is an uninterpreted function with a width law.
   C1 is exact injectivity on the 32-byte payment-preimage domain only.  For
   P2WSH the relevant input is a 71-byte script; exact injectivity there is
   impossible with a 32-byte output.  The honest mechanized form is the
   finite pair admission used here.  A computational "no efficient collision
   finder" statement is outside the model and is not claimed.
3. **No P2WSH / `OP_CHECKMULTISIG` interpreter bridge.**  The imported
   `Bitcoin.Data.Script.parse` has no `OP_CHECKMULTISIG` constructor
   (`vendor/btc-lean-core/Bitcoin/Data/Script.lean:31-41`), and
   `FundingProps.witnessScript_parse_eq_none_of_wellFormed` proves it rejects
   the BOLT 3 funding script.  `Bitcoin.Interpreter` is not imported/connected
   to the BOLT 3 witness shape.  Therefore this module proves the output
   format and hash commitment, **not** consensus-level spendability by the
   2-of-2.  The missing bridge is a verified `verifyScript`/witness-stack
   semantics for P2WSH v0 plus `OP_CHECKMULTISIG`, as named by
   `FundingSpendBridge.script_semantics` in `PhaseC2/FundingBridge.lean`.
4. **C2 is not a blocker for this row.**  HASH160 collision resistance is
   irrelevant to P2WSH.  It should not be added as a hypothesis to
   `LN-L1-001`.
5. **Key validity is length-only.**  `PubKey.Valid` only checks 33 bytes; the
   non-vacuity witness uses zero/one byte strings, not real secp256k1 points.
   This does not affect the structural theorem, but any claim about real keys
   additionally needs a secp256k1 encoding/validity model.
