## Verdict

The catalog target `LnLean.Channel.HTLC.id_unique` **cannot be promoted as
written**: it still assumes `liveHtlcIdsNodup hs`, which is the uniqueness
property being claimed. I added a channel-level allocator (`HtlcBook`) with the
two BOLT 2 per-sender id counters, proved its invariant from construction, and
derived **per-sender live-id uniqueness unconditionally for every book built by
the allocator**. The public retarget candidate is

```lean
LnLean.Channel.HTLC.dir_id_unique
```

with no id-distinctness hypothesis (only a constructor trace `b.Reachable`).

The literal **global** wording ("unique within the live HTLC set of a
channel") is **false for the faithful BOLT 2 model**, and this is mechanized:
the allocator itself can produce a reachable book containing a live local id 0
and a live remote id 0, because each sender owns an independent counter that
starts at 0. The global form is therefore also available only under an explicit
cross-direction disjointness premise, and the catalog should either narrow the
English claim or use that conditional target.

### State and allocation API

```lean
structure HtlcBook where
  records : List HTLCRecord
  nextLocalId : Nat
  nextRemoteId : Nat

namespace HtlcBook

def empty : HtlcBook
def nextId (b : HtlcBook) : Direction → Nat
def liveOf (b : HtlcBook) (dir : Direction) : List HTLCRecord
def liveIdsOf (b : HtlcBook) (dir : Direction) : List Nat
def liveIds (b : HtlcBook) : List Nat
def totalInFlight (b : HtlcBook) : Msat
def allocate (b : HtlcBook) (dir : Direction) (amount : Msat)
    (ph : PaymentHash) (cltv : Height) : HTLCRecord
def push (b : HtlcBook) (dir : Direction) (r : HTLCRecord) : HtlcBook
def insert (b : HtlcBook) (dir : Direction) (amount : Msat)
    (ph : PaymentHash) (cltv : Height) : HtlcBook
def add (b : HtlcBook) (maxHtlcValue : Msat) (dir : Direction)
    (amount : Msat) (ph : PaymentHash) (cltv : Height) : Result HtlcBook
```

`allocate` takes the id from the sender's counter (`0, 1, 2, ...` per sender),
`push` inserts and advances only that sender's counter, `insert` is
allocate-then-push, and `add` runs the **existing** `addHTLC` guard with the
allocated id and `b.totalInFlight`; a rejected add changes neither records nor
counters. This is the BOLT 2 rule at
`refs/bolts/02-peer-protocol.md:2838-2843`, matching rust-lightning's
`next_holder_htlc_id` / `next_counterparty_htlc_id`
(`lightning/src/ln/channel.rs:3719-3720`).

### Invariant and reachability

```lean
structure WF (b : HtlcBook) : Prop where
  bound_local : ∀ r ∈ htlcSet b.records, r.direction = .local →
    r.id < b.nextLocalId
  bound_remote : ∀ r ∈ htlcSet b.records, r.direction = .remote →
    r.id < b.nextRemoteId
  nodup_local : (b.liveIdsOf .local).Nodup
  nodup_remote : (b.liveIdsOf .remote).Nodup

inductive Reachable : HtlcBook → Prop where
  | empty : Reachable empty
  | insert {b} (hb : Reachable b) (dir) (amount) (ph) (cltv) :
      Reachable (b.insert dir amount ph cltv)
  | add {b} (hb : Reachable b) (maxHtlcValue) (dir) (amount) (ph) (cltv)
      {b'} (ok : b.add maxHtlcValue dir amount ph cltv = .ok b') :
      Reachable b'
```

The `bound_*` fields are not the uniqueness conclusion: they are what proves
that the next counter value is fresh for the sender. The `nodup_*` fields are
an inductive invariant established at `empty` and preserved only because the
new id equals the counter and every old live id is strictly below it. The
public per-sender theorem below quantifies over `Reachable`, so it does **not**
assume `WF` or any id-distinctness property.

## Proof strategy

1. **Allocation.** `allocate` constructs the record at `b.nextId dir` and
   starts it `offered` (local) or `received` (remote). `push` prepends it and
   increments exactly that sender's counter. `add` reuses the existing
   `addHTLC` guard so the model transition is not bypassed.
2. **Counter freshness.** `liveIdsOf_lt_next` reads the counter bound out of
   `WF`; `nextId_not_mem_liveIdsOf` turns it into `b.nextId dir ∉
   b.liveIdsOf dir`. This is the step the old target was missing: freshness is
   *derived*, not assumed.
3. **Invariant preservation.** `push_wf` splits on the sender. The new record
   is live, has the sender's counter as id, and every old live id of that
   sender is strictly below the counter (`Nat.lt_trans … (Nat.lt_succ_self _)`).
   The other sender's records and counter are untouched. `insert_wf` and
   `add_wf` instantiate it; `empty_wf` is the base case.
4. **Construction trace.** `Reachable` records the two ways a book is built
   (counter insertion or successful guarded add). `reachable_wf` is the
   induction that packages the invariant for all reachable states.
5. **Per-sender uniqueness.** `liveIdsOf_nodup` exposes the per-sender
   distinctness; `eq_of_id_eq_of_htlcIds_nodup` (already in the module) turns
   it into the relational statement `liveOf_id_unique`. Therefore
   `reachable_liveOf_id_unique` / `HTLC.dir_id_unique` have **no uniqueness
   hypothesis** — only `b.Reachable`.
6. **Global form.** `CrossDisjoint` says no live local id equals a live remote
   id. `liveIds_nodup_of_cross` combines the two per-sender `Nodup` lists via
   `List.nodup_append` and transports along the already-proved
   `htlc_filter_direction_perm`; `live_id_unique_of_cross` then applies the
   core list lemma. This premise is exactly the cross-sender part, and it is
   **not** implied by per-sender counters.

## Faithful counterexample / why the global wording is false

`crossBook` is built by the new allocator from `empty`:

```lean
def crossBook : HtlcBook :=
  (empty.insert .local ⟨1000⟩ sampleHash 500).insert
    .remote ⟨2000⟩ sampleHash 600
```

`crossBook_wf` and `crossBook_reachable` are proved. Its live ids are `[0, 0]`
(`crossBook_liveIds`), so `crossBook_not_liveHtlcIdsNodup` proves
`¬ liveHtlcIdsNodup crossBook.records`, and
`reachable_cross_direction_duplicate` proves

```lean
∃ b : HtlcBook, b.Reachable ∧ ¬ liveHtlcIdsNodup b.records.
```

This is not a modelling bug: BOLT 2 allocates ids independently per sender, and
both counters start at 0. A local HTLC with id 0 and a remote HTLC with id 0
are protocol-conforming. Consequently no unconditional *global* theorem can be
proved without strengthening the model (see “Remaining blockers”).

The existing counterexample `addHTLC_same_id_distinct_amounts_ok` is retained
unchanged: `addHTLC` still accepts two adds with id 7 and different amounts.
The new `insert`/`add` API is the safe wrapper that prevents the *sender* from
doing that through allocation.

## Catalog recommendation

**Do not promote `LnLean.Channel.HTLC.id_unique`.** Its signature is still

```lean
theorem id_unique (hs : List HTLCRecord)
    (hnd : liveHtlcIdsNodup hs) :
    ∀ h1 ∈ htlcSet hs, ∀ h2 ∈ htlcSet hs, h1.id = h2.id → h1 = h2
```

and `hnd` is the claimed property.

Recommended retarget (narrowed English claim):

> An HTLC id is unique among the live HTLCs of one sender in a channel.

Exact Lean target:

```lean
LnLean.Channel.HTLC.dir_id_unique
```

This is unconditional for every book built by the allocator (`b.Reachable`),
with no separate distinctness assumption. If a `WF`-style hypothesis is
preferred, `LnLean.Channel.HTLC.dir_id_unique_of_wf` is the same theorem from
the allocator invariant.

If the catalog must retain the literal **global** wording, the only faithful
target is conditional:

```lean
LnLean.Channel.HTLC.id_unique_of_reachable_cross   -- b.Reachable + b.CrossDisjoint
-- or
LnLean.Channel.HTLC.id_unique_of_cross             -- b.WF + b.CrossDisjoint
```

The `CrossDisjoint` premise is exactly the cross-sender part and is not a
consequence of the per-sender counters; `reachable_cross_direction_duplicate`
shows it can fail for a reachable book. Promoting the global wording without
that premise would be unsound.

## Remaining blockers / exact missing model change

* **Per-sender uniqueness: no blocker.** It is proved from construction, with
  the freshness of each allocation derived from the counter bound.
* **Global uniqueness: blocked by the protocol itself.** BOLT 2 ids are
  per-sender (`update_add_htlc.id` is interpreted together with the sending
  direction), and both endpoints start at 0. To obtain a global theorem one
  would have to change the model so that both peers share a single id
  namespace — for example direction-tagged ids (`2*id` for local, `2*id+1`
  for remote) or a single channel-wide counter. That is a model/protocol
  extension, not a theorem about BOLT 2 as modelled, and I did not make it
  silently.
