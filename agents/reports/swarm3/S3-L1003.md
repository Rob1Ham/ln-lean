## 1. Why the row needs a retarget

The catalog row currently names

```lean
LnLean.Security.Adversary.reorgAllowed : Adversary → Reorg → Prop
```

which is a **definition** (`r.depth ≤ a.reorgBudget`), not a theorem. The
catalog checker's promotion rule requires a theorem/lemma, so the row cannot
leave `statementOnly` while it names that `def`. The claim also has two halves
that the `def` does not state: (i) preservation under a depth-bounded reorg
with a common chain tip, and (ii) a separate deep-reorg failure mode.

`LnLean/Proofs/Security/ReorgTargets.lean` supplies both, plus the negative
result showing the unconditional reading is false. It is deliberately
self-contained on `LnLean.Security.Model` + `LnLean.Security.Invariants`; it
does **not** import `LnLean.Proofs.WaveD.D02`, because `D02` depends on
`LnLean.Channel.HTLC`, which was being edited concurrently by another lane and
had no valid `.olean` at build time. The D02 correspondence is documented in
§8 of the module and in §8 below.

## 2. Exact signatures

Core vocabulary:

```lean
abbrev antiReorgDelay : Nat := 6

abbrev confirmationCount (tip h : Height) : Nat := tip + 1 - h

abbrev reorgSurvives (r : Reorg) (tip h : Height) : Prop :=
  r.depth < confirmationCount tip h

def SameChain (v w : ChainView) : Prop :=
  v.height = w.height ∧ v.tip = w.tip

def InCommonPrefix (v : ChainView) (r : Reorg) (h : Height) : Prop :=
  h + r.depth ≤ v.height

structure OnchainFact where
  height : Height
  amount : Msat

structure Observations where
  ledger : Ledger
  facts : List OnchainFact

def Observations.SafeAt (o : Observations) (v : ChainView)
    (a : Adversary) : Prop :=
  o.ledger.Conserves ∧
    ∀ e ∈ o.facts, a.reorgBudget < e.confirmations v.height

def Observations.OnchainSafeAt (o : Observations) (v : ChainView) : Prop :=
  ∀ e ∈ o.facts, antiReorgDelay ≤ e.confirmations v.height

def Observations.OutOfReachOf (o : Observations) (v : ChainView)
    (r : Reorg) : Prop :=
  ∀ e ∈ o.facts, r.depth < e.confirmations v.height

def Observations.applyReorgAt (o : Observations) (tip : Height)
    (r : Reorg) : Observations :=
  { o with facts := o.facts.filter (fun e => decide (e.survives r tip)) }

def Retains (o o' : Observations) : Prop :=
  o'.ledger = o.ledger ∧ ∀ e ∈ o.facts, e ∈ o'.facts
```

Positive targets:

```lean
theorem reorg_preserves_channel_safety
    {o : Observations} {v w : ChainView} {a : Adversary} {r : Reorg}
    (hsame : SameChain v w)
    (hsafe : o.SafeAt v a)
    (hallowed : a.reorgAllowed r) :
    Retains o (o.applyReorgAt v.height r) ∧
      (o.applyReorgAt v.height r).SafeAt w a

theorem reorg_preserves_channel_safety_within_anti_reorg_delay
    {o : Observations} {v w : ChainView} {a : Adversary} {r : Reorg}
    (hsame : SameChain v w)
    (hconserves : o.ledger.Conserves)
    (hsettled : o.OnchainSafeAt v)
    (hbudget : a.reorgBudget < antiReorgDelay)
    (hallowed : a.reorgAllowed r) :
    Retains o (o.applyReorgAt v.height r) ∧
      (o.applyReorgAt v.height r).SafeAt w a

theorem reorg_retains_of_depth_bound {o : Observations} {v : ChainView}
    {r : Reorg} (hreach : o.OutOfReachOf v r) :
    Retains o (o.applyReorgAt v.height r)
```

The first theorem is the catalog target. The conjunction matters: `SafeAt`
alone is closed under dropping facts, so `Retains` is the load-bearing
conjunct. The per-reorg form `reorg_retains_of_depth_bound` is the literal
"one reorg within the stated depth" reading; the budget form is what makes
the statement hold for every allowed reorg.

Deep-reorg / negative targets:

```lean
theorem deep_reorg_separate_failure_mode (r : Reorg)
    (hdeep : antiReorgDelay ≤ r.depth) :
    ∃ (v : ChainView) (o : Observations) (e : OnchainFact),
      o.SafeAt v budgetFiveAdversary ∧
        e ∈ o.facts ∧
        e ∉ (o.applyReorgAt v.height r).facts

theorem deep_reorg_not_allowed (r : Reorg)
    (hdeep : antiReorgDelay ≤ r.depth) :
    ¬ budgetFiveAdversary.reorgAllowed r

theorem safety_not_unconditional :
    ¬ (∀ (o : Observations) (v : ChainView) (a : Adversary) (r : Reorg),
        o.OnchainSafeAt v → a.reorgAllowed r →
          Retains o (o.applyReorgAt v.height r))
```

Common-tip necessity:

```lean
theorem safeAt_congr_of_sameChain {o : Observations} {v w : ChainView}
    {a : Adversary} (h : SameChain v w) :
    o.SafeAt v a ↔ o.SafeAt w a

theorem common_tip_needed :
    ∃ (v w : ChainView) (r : Reorg) (e : OnchainFact),
      ¬ SameChain v w ∧ e.survives r v.height ∧ ¬ e.survives r w.height

theorem safety_judgement_needs_common_tip :
    ∃ (o : Observations) (v w : ChainView) (a : Adversary),
      o.SafeAt v a ∧ ¬ o.SafeAt w a
```

## 3. Assumptions kept explicit

1. **Common chain tip (`SameChain`).**  The two parties must agree on both
   observed height and tip hash. The wave-A model has no block-hash-per-height
   map and no consensus rule, so this is a hypothesis. It is not decorative:
   `safety_judgement_needs_common_tip` exhibits one observation that is safe at
   one view (height 10, fact confirmations 11, budget 8) and unsafe at another
   (height 6, confirmations 7, same budget). `safeAt_congr_of_sameChain` is the
   positive counterpart.
2. **Common prefix / confirmation arithmetic.**  A fact at height `h` is
   outside a depth-`d` reorg iff `h + d ≤ tip`, equivalently
   `d < confirmationCount tip h`. `InCommonPrefix` and `survives_iff_prefix`
   state this. The model has no replacement-chain height, so `applyReorgAt`
   keeps the observed pre-reorg tip for accounting and updates only *which
   facts are retained*. Post-reorg confirmation depth is not claimed.
3. **Bounded reorg depth.**  Two explicit forms: `OutOfReachOf v r` bounds the
   given reorg; `SafeAt v a` bounds the adversary's entire budget. The latter
   is required for "every allowed reorg" and is what rules out the depth-six
   counterexample. `a.reorgAllowed r` alone is only `r.depth ≤ a.reorgBudget`
   and proves nothing about survival.
4. **Ledger unchanged by an L1 reorg.**  The in-channel `Ledger` is not
   rewritten; only on-chain facts can be evicted. This is a model limitation,
   not a consensus theorem.
5. **Anti-reorg delay = 6.**  `antiReorgDelay` is the BOLT 5 / LDK
   `ANTI_REORG_DELAY` constant, not a Bitcoin consensus rule. The
   `within_anti_reorg_delay` corollary assumes the adversary's whole budget is
   strictly below it.
6. **Outside the model.**  No Bitcoin consensus, no block-level common-prefix
   object, no transaction/script spend semantics, no probabilistic reorg
   model. The deep-reorg result proves eviction of an observed resolution, not
   theft; actual deep-reorg theft/double-spend remains `LN-CHAIN-REORG`.

## 4. Non-vacuity

`settledObservations` conserves `1000 msat` (`600 + 400 + 0 + 0`) and relies
on one funding fact at height 0. `settledView` has tip height 5, giving that
fact `6 = antiReorgDelay` confirmations. `budgetFiveAdversary` has
`reorgBudget = 5`.

* `settledObservations_safe : settledObservations.SafeAt settledView budgetFiveAdversary`
* `settled_reorg_preserves`: a depth-five reorg (allowed) both retains the
  fact and preserves safety.
* `settled_reorg_retains`, `settled_fact_still_present`: the fact is still in
  the filtered list, so the positive instance does not silently drop
  everything.
* `deep_reorg_separate_failure_mode`: for every depth ≥ 6, that same settled
  channel loses the fact; `deep_reorg_not_allowed` confirms the reorg is
  outside the depth-five budget.
* `safety_not_unconditional`: a depth-six adversary plus a depth-six reorg
  evicts a six-confirmation fact, so "settled + `reorgAllowed`" without the
  budget bound is false.
