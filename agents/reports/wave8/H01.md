## Exact result

The lane target was
`txCheckerFor tx nIn (some amount) = realCheckerOf tx nIn amount` for
`nIn < tx.vin.length`. The equality is in fact **unconditional**: both
definitions use the same `Bitcoin.Capstone.RealChecker.dummyTxIn` for the
sequence environment, and for `some amount` the pipeline's
`Option.getD`/`Option.isSome` fields reduce to `amount`/`true`. The only
non-definitional difference is the Schnorr slot (`txCheckerOf` uses
`schnorrVerdict verify (fun _ _ _ => none)`; `realEcdsaEntry` uses the literal
`fun _ _ _ _ => false`); the former is pointwise `false`, so the checkers are
equal.

```lean
theorem schnorrVerdict_sighash_none_false
    (verify : ByteArray → ByteArray → ByteArray → Bool)
    (sig pk : ByteArray) (v : SigVersion) (d : ScriptExecutionData) :
    schnorrVerdict verify (fun _ _ _ => none) sig pk v d = false

theorem txCheckerOf_eq_ecdsaEntry_of_sighash_none
    (verify : ByteArray → ByteArray → ByteArray → Bool)
    (sighash : ByteArray → UInt8 → SigVersion → ByteArray)
    (hasAmount : Bool)
    (verifySchnorr : ByteArray → ByteArray → ByteArray → Bool) :
    txCheckerOf verify sighash hasAmount verifySchnorr (fun _ _ _ => none)
      = ecdsaEntry verify sighash hasAmount

    (hbase : c₁.base = c₂.base) (henv : c₁.env = c₂.env) : c₁ = c₂

        c₂.checkECDSASignature sig pk code v d)
```

## Scope caveats

- **The equality is at the `ScriptChecker` level.** It is exact, including
  both signature entry points and the `LocktimeEnv`. Any interpreter/script
  execution using the checker (e.g. `verifyWitnessProgram`,
  `verifyScriptFull`, `scriptLaneTx`) therefore has the same result under both
  checkers by congruence; this module states the delayed `to_local` payoff
  explicitly and leaves the other branch transports to lanes H02–H04.
- **`none` is a fail-closed missing-data state, not an amount.** In
  `txCheckerFor tx nIn none`, `hasAmount = false` and the dummy amount is `0`.
  Witness-v0 ECDSA checks are then false for every input
  (`txCheckerFor_none_ecdsa_witnessV0`); legacy (`base`), `taproot` and
  `tapscript` ECDSA verdicts are unchanged from the `some amount` checker
  (`txCheckerFor_none_ecdsa_eq_some_of_ne`). There is no `realCheckerOf`
  analogue for `none` (that definition always takes an amount and uses
  `hasAmount = true`).
- **Taproot/script-path spends remain unadjudicated.** `txCheckerFor`'s
  Schnorr entry uses the fail-closed `sighashSchnorr = fun _ _ _ => none`, so
  every Schnorr check is `false` in both checkers. This is exactly the
  pipeline's "unjudged" BIP342 stand-in, not a consensus claim; it is also why
  the two checkers can be equal.
- **No consensus/EC claim is added.** `Bitcoin.Crypto.Ecdsa.Verify.verifyImpl`
  is the vendored lax secp256k1 implementation; assumption C3 (EUF-CMA) is
  still not proved. The spent `amount` remains an explicit context parameter,
  and this lane does not prove it equals the referenced outpoint value.
- `csv < 32768` / `to_self_delay` range and `minimalData` policy edges are
  outside this lane (H05/H06), as is the concrete-vendor ECDSA instantiation
  (H29–H32).
