- Theorems/definitions:
  - `waveD_d43_revocationBranch`, `waveD_d43_delayedPrefix`,
    `waveD_d43_delayedBranch`, `waveD_d43_scriptTail`: the two literal byte
    segments of the BOLT 3 template.
  - `waveD_d43_toLocal_branch_decomposition`: unconditional exact equation
    `toLocalWitnessScript rev del d`.bytes =
    `OP_IF <rev> ++ OP_ELSE <delay> OP_CSV OP_DROP <del> ++ OP_ENDIF OP_CHECKSIG`.
    This is the core "revocation branch vs delayed-payment branch" separation.
  - `waveD_d43_toLocal_revocationKey_injective`: for 33-byte revocation keys,
    equality of two `to_local` witness scripts implies equality of the
    revocation keys, with **no** hypothesis on the delayed keys or delays.
  - `waveD_d43_toLocal_delayedPaymentKey_injective`: with the revocation key and
    delay fixed, equality of scripts implies equality of delayed-payment keys.
  - `waveD_d43_toLocal_revocationKey_not_delayedBranch`: when the keys differ,
    the delayed key is not the key pushed after `OP_IF`.
  - `waveD_d43_toLocal_role_swap_changes`: swapping revocation and delayed key
    roles changes the script.
  - `waveD_d43_p2wsh_injective`: the P2WSH program determines its 32-byte
    witness-script hash.
  - `waveD_d43_toLocalScriptPubKey_commits_revocationKey`: under a collision-free
    `sha256` (parameter) and `CommitmentParams.HashesMatch`, equal
    `toLocalScriptPubKey` values imply equal revocation keys; contrapositive in
    `waveD_d43_toLocal_distinct_revocationKeys_distinct_script`.
  - `waveD_d43_commitmentOutputs_toLocal_output`: the `.toLocal` member of
    `commitmentOutputs` is exactly this P2WSH output, so the result applies to
    the commitment output list.
  - `waveD_d43_toLocal_commits_derived_revocationKey`: equal scripts imply equal
    `RevocationScheme`-derived revocation keys.
  - `waveD_d43_toLocal_commits_commitmentNumber`: conditional composition with
    `Shachain`/`RevocationScheme` recovering the commitment number.
- Added hypotheses:
  - `waveD_d43_toLocal_revocationKey_injective` assumes both revocation keys are
    valid compressed keys (`bytes.size = 33`). This is needed to cancel the two
    equal-length `pushData` prefixes; 33-byte validity is the model's
    `PubKey.Valid`/`RevocationKey.Valid` condition.
  - `waveD_d43_toLocalScriptPubKey_commits_revocationKey` assumes a
    collision-free `sha256 : Script → ByteArray` and the existing
    `CommitmentParams.HashesMatch` bridge. SHA-256 is deliberately not
    implemented in the model (`ScriptTemplates` documents this gap), so the
    hash assumption is explicit rather than axiomatized.
  - `waveD_d43_toLocal_commits_commitmentNumber` additionally assumes
    (a) every derived `revocationPubkeyOfSecret` key is 33 bytes and
    (b) `RevocationScheme.pointOf` is injective on per-commitment secrets.
    Neither field exists in `LnLean.Channel.RevocationScheme`; these are the
    named missing model invariants for commitment-number binding.
- Statement fidelity:
  - The witness-script commitment claim is proved **unconditionally** over the
    exact bytes produced by `toLocalWitnessScript`; nothing about the delayed
    key or delay is assumed. No theorem is weakened by dropping the revocation
    key.
  - The output-script (`P2WSH`) version only adds the standard crypto bridge;
    it does not assume the revocation key is recoverable without the hash.
  - "Distinguish from the delayed-payment path" is modelled structurally:
    the revocation key is the first push in the `OP_IF` branch, while the
    delayed-payment key follows `OP_ELSE` + `to_self_delay` + `OP_CSV` +
    `OP_DROP`. The script binds both keys but in asymmetric roles, and role
    swapping changes the script.
  - No `sorry`, `axiom`, `admit`, `native_decide`, `unsafe`, Mathlib, or extra
    dependency. Only the four brief imports are used.

## Remaining gap / next step

- SHA-256 collision resistance is an external cryptographic assumption, not a
  Lean theorem; the P2WSH commitment corollary must therefore remain
  conditional until a concrete SHA-256 model with an injectivity/collision
  bound exists.
- `RevocationScheme` lacks `derivePubkey` validity and `pointOf` injectivity,
  so recovering the commitment number is conditional. Adding those fields (and
  a proof that the abstract derivation is the BOLT 3 secp256k1 derivation)
  would remove the hypotheses from `waveD_d43_toLocal_commits_commitmentNumber`.
- No script interpreter / signature checking is modelled; these are byte-shape
  and commitment results, not spendability results.
