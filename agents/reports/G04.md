# G04 — Wave-D vs Wave-E audit: targets 07 and 08

Scope: `LN-CR-003` (D07/E07, onion HMAC integrity) and `LN-CR-004` (D08/E08,
BigSize round trip). Read-only audit: no Lean edits, no `lake build`, no git
writes. `sorry` counts below are after stripping nested block comments and
line comments. Green evidence is from existing artifacts only: source mtimes,
`.olean`/`.trace` mtimes, trace `outputs.o` vs `.olean.hash`, and declaration
name strings in the oleans. The relevant base modules are byte-identical in
the two trees (`Crypto/Model.lean`, `Crypto/Hash.lean`, `Routing/Onion.lean`,
`Wire/BigSize.lean`, `Proofs/Obligations.lean` all compare equal), so the
comparison is apples-to-apples.

## Target 07 — LN-CR-003: "Onion integrity checks are HMAC-SHA256 tags, relying on C8"

**Verdict: D — `/home/ubuntu/ln-lean/LnLean/Proofs/WaveD/D07.lean`.**
**Confidence: 0.62 (medium; narrow win on fidelity, not on breadth).**

### Evidence

- **Real `sorry` sites: 0 in both.** D07 and E07 contain no code-level `sorry`
  (D07/E07 raw text also has none outside comments). Neither olean contains a
  `sorryAx` string. No `axiom`, `admit`, `native_decide`, `unsafe`,
  `@[implemented_by]`, or `opaque` in either source.
- **Green exact-module evidence: both green.** D07 source mtime
  `2026-10-17 23:32:53`, olean `23:33:08`; E07 source `23:45:18`, olean
  `23:47:34`. Traces exist and their `outputs.o` hashes equal the respective
  `.olean.hash` files (D07 `582af24a5cf16e46`, E07 `9505f0543a808822`), so the
  trace belongs to the current olean. Required dependencies are older
  (`Crypto.Model` 22:27:26; `Routing.Onion` 22:29:54 in D, 23:42:33 in E) and
  the trace log has only a `trace` entry, no errors/warnings. Reports claim
  RC 0, consistent with the artifacts. All expected `waveD_d07_*` /
  `waveE_e07_*` names are present in the olean strings.
- **Statement fidelity: D is better.**
  - D07 `onionHmacTag` (lines 77–79) is exactly
    `HMAC256(mu, hop_payloads || associated_data)`, and
    `hmacOnionInterface` (133–135) keeps the base interface's documented
    argument order: `verifyHmac expected stored = decide (expected = stored)`.
    `openWithHmac` (148–150) computes the BOLT tag and passes it as the
    `tag` argument of `openLayer`, matching `Routing/Onion.lean:298,305–311`.
    Under C8, `waveD_d07_openWithHmac_layer_authentic` (168–181) yields both
    the tag identity and uniqueness of `hop_payloads` for fixed associated
    data.
  - E07's HMAC check (`hmacVerify`, 95–96) is correct, but `hmacInterface`
    (176–178) treats `verifyHmac`'s first argument as the *covered byte
    string*, while `Routing/Onion.lean` documents that slot as the expected
    `tag` (`openLayer` passes `tag`, 305–311). E07 documents this
    reinterpretation (172–175), but the instantiation is not drop-in for
    downstream callers and does not state expected-tag-vs-stored-tag
    comparison directly. Its `layerTag` (143–144) also uses the layer's
    opaque `ciphertext` as a stand-in for the BOLT-covered bytes, whereas
    BOLT 4 covers `hop_payloads || associated_data`; D07 models that message
    explicitly.
- **Added hypotheses: effectively a tie, D more transparent.** D07 takes
  `hC8 : HmacPrf M.hmacSha256` explicitly on the binding theorems
  (104–108, 114–117, 168–175); it is discharged immediately by
  `M.hmac_prf` (`waveD_d07_c8_from_model`, 97–98), so it is not a weakening.
  E07 carries C8 implicitly as the required `PrimitiveModel.hmac_prf` field
  and adds no explicit hypothesis. Both are conditional on the same model
  field.
- **Positive/counterexample content: E is stronger.** E07 has 18 theorems vs
  D07's 10: completeness/soundness/rejection of the verifier (99–136),
  layer-validity characterisation (157–168), packet-level binding
  `waveE_e07_openLayer_covered_eq` (219–240), and two mechanized C8-necessity
  results — `constantHmac` is not `HmacPrf` (249–257) and the bare tag
  comparison accepts one tag for two distinct covered strings (263–273).
  D07's counterexample (`permissiveOnionInterface`,
  `waveD_d07_abstract_interface_accepts_any_tag`, 189–199) is a near-trivial
  witness that the base interface is unconstrained, though it does document
  a genuine model gap. D07's payload-uniqueness/no-reuse theorems (104–126)
  cover the same binding content as E07's `_binds`/`_covered_eq`.
- **Names/markers/catalog.** Both have exactly one well-formed unique marker
  (`LN-WD-D07` at D07:69, `LN-WE-E07` at E07:194; E07's marker sits between a
  docstring and its theorem, which is legal but stylistically fragile). Both
  use unambiguous namespaces. Both correctly note that the catalog target
  `LnLean.Crypto.Hash.hmacSha256` is not a declaration; the real operation is
  the field `PrimitiveModel.hmacSha256` (`Crypto/Model.lean:94`, with
  `HmacPrf` at 77–79). Neither creates an alias at the catalog path, so a
  name-resolution check against `Obligations.lean` still fails for both.
- **Report accuracy.** D07 reports `conditional`, which is the honest status
  (C8 is an assumption field; the model's `HmacPrf` is injectivity, stronger
  than a computational PRF). E07 reports `proved`, which overstates the
  result for the brief's status vocabulary; its own "Remaining gap" still
  admits the computational/PRF gap.

### Caveats

- No rebuild was performed. Greenness rests on olean-newer-than-source,
  trace/hash consistency, and import ordering; the source content hash in the
  trace was not independently recomputed.
- E07 is a defensible alternative if theorem breadth and C8-necessity
  counterexamples are weighted above interface fidelity. The two modules are
  close enough that 0.62 reflects a judgment call.
- Neither lane updates `Obligations.lean` (`LN-CR-003` is still
  `statementOnly`, lines 130–135) or `Traceability.lean` (stale target at
  line 218); integration bookkeeping must be done separately.

## Target 08 — LN-CR-004: "BigSize encoding and decoding are inverse on canonical encodings"

**Verdict: D — `/home/ubuntu/ln-lean/LnLean/Proofs/WaveD/D08.lean`.**
**Confidence: 0.88 (high).**

### Evidence

- **Real `sorry` sites: 0 in both.** D08's only textual `sorry` is the
  docstring at line 39 ("No `sorry`…"); E08 has none. Neither olean contains
  `sorryAx`. No forbidden tactics/axioms in either source.
- **Green exact-module evidence: both green.** D08 source mtime
  `2026-10-17 23:58:52`, olean `2026-10-18 00:00:26`; E08 source `23:49:55`,
  olean `23:51:57`. Trace `outputs.o` equals `.olean.hash` in both (D08
  `f5e7c1218f14f4c5`, E08 `c458838550215230`). `Wire.BigSize` oleans predate
  the modules (23:42:25 in E; D's are older), and all expected declaration
  names appear in the olean strings. Both reports claim RC 0; artifacts are
  consistent. D modules are committed (`git status` clean); E modules are
  still untracked in the Wave-E tree — an integration caveat, not a proof
  defect.
- **Statement fidelity: D is stronger and more exact.**
  - D08 `waveD_d08_decode_encode` (67–69) restates the catalog target by
    citing `LnLean.Wire.decode_encode` directly (the actual theorem is at
    `Wire/BigSize.lean:356`; the catalog string
    `LnLean.Wire.BigSize.decode_encode` is a stale namespace).
  - E08 re-derives the same statement from the four range lemmas (66–78),
    which is a useful independent check but not stronger.
  - The catalog claim is a *two-sided* inverse on canonical encodings. D08
    mechanizes the missing direction for arbitrary bytes:
    `waveD_d08_decode_full_canonical` (241–414) and the iff
    `waveD_d08_decode_full_iff` (420–434): a full-length successful decode is
    exactly a canonical encoding. That is the substantive converse.
  - E08's converse (`waveE_e08_canonical_roundtrip`, 115–127;
    `canonical_unique`, 132–140) assumes `b` is already canonical and is
    therefore close to a restatement of the forward theorem. It does not
    characterize arbitrary byte arrays.
- **Added hypotheses.** Both use the model's `n < 2^64` domain and a
  canonicality hypothesis on the converse. D08's arbitrary-byte converse
  additionally assumes `len = b.size` (a complete, not prefix, decode) — this
  is documented and is what makes the strong converse meaningful, not a
  weakening. D08's `decode_full_iff` packages the domain bound and full
  consumption into one two-sided statement.
- **Positive/counterexample content: D is clearly stronger.** D08 has 20
  theorems including digit-uniqueness lemmas (`decodeBEList_lt/_inj`,
  `beBytesAux_decodeBEList`, `bytesToList_inj`, 130–226), four kernel-checked
  non-canonical rejections, two short-read rejections, an accepted lower
  boundary (443–480), and the truncation counterexample above `2^64`
  (`encode (2^64)` is the all-zero `0xff` payload and `decode` rejects it,
  490–502), plus the failed-round-trip corollary (498–502). E08 has 18
  theorems with three non-minimal rejections (265–279) but no truncation
  counterexample and no arbitrary-byte converse.
  E08 does contain one genuinely extra result D08 lacks: domain closure
  `waveE_e08_decode_value_lt` (227–260), showing every successful decode lands
  below `2^64`.
- **Names/markers/catalog.** Both have exactly one well-formed marker
  (`LN-WD-D08`, `LN-WE-E08`), no duplicates, no malformed markers, and
  unambiguous namespaces. Neither provides the literal catalog declaration
  `LnLean.Wire.BigSize.decode_encode` (the real name is
  `LnLean.Wire.decode_encode`); both restate under wave-local names. D08's
  report repeats the stale catalog name without flagging the namespace typo;
  E08's header does the same. Minor report/bookkeeping issue for both.
- **Report accuracy.** Both report `proved` and RC 0, consistent with the
  claims (the only hypotheses are the model domain and documented
  canonical/full-decode conditions). E08's claim that `#print axioms` shows
  only `propext`/`Quot.sound` was not independently re-run (read-only audit);
  the source contains no `axiom`/`sorry`, so the claim is plausible but
  unverified here.

### Caveats

- D08's module header says "the only hypothesis is the model's documented
  domain restriction `n < 2^64`", but several theorems also take
  `IsCanonicalEncoding` or `len = b.size`; the report documents these
  correctly, so this is only a header imprecision.
- No rebuild was performed; greenness is inferred from timestamps, trace
  hashes, and olean symbols as above.
- E08's independent re-derivation of `decode_encode` is valuable as a
  cross-check even though D08's direct citation is more faithful to the
  catalog target.

## Overall recommendation

- **07:** Adopt **D07**. It matches the BOLT 4 tag construction and the
  `openLayer` expected-tag/stored-tag contract, states the C8-dependent
  uniqueness result cleanly, and its report honestly says `conditional`.
  If breadth matters, graft E07's `waveE_e07_constantHmac_not_prf` and
  `waveE_e07_tag_check_needs_c8` into the adopted module; do not adopt E07's
  interface instantiation without fixing the first-argument convention.
- **08:** Adopt **D08**. It proves the genuine two-sided characterization
  (arbitrary-byte full decode iff canonical encoding), includes stronger
  concrete rejection and truncation evidence, and cites the exact model
  theorem. Graft E08's `waveE_e08_decode_value_lt` as a useful domain-closure
  supplement.
- **Bookkeeping (both targets):** fix the stale catalog targets —
  `PrimitiveModel.hmacSha256` (not `LnLean.Crypto.Hash.hmacSha256`) and
  `LnLean.Wire.decode_encode` (not `LnLean.Wire.BigSize.decode_encode`) — or
  add explicit aliases; update `Obligations.lean`,
  `agents/status/obligations.json`, `Traceability.lean`, and the generated
  docs, which still mark both entries `statementOnly` and encode the stale
  names. Record 07 as conditional (C8), 08 as proved on the `uint64` domain.

   `HMAC(mu, hop_payloads || associated_data)` tag and correct expected/stored

   genuine arbitrary-byte full-decode iff, digit uniqueness, seven concrete
   rejection/boundary checks, and a `2^64` truncation counterexample; E08's
   converse is canonical-only and near-definitional.

   zero `sorryAx`, oleans newer than sources, trace output hashes matching
   `.olean.hash`, and all expected declaration names present; no rebuild was
   run.

   08); neither touches the catalog, whose targets remain stale
   (`LnLean.Crypto.Hash.hmacSha256`, `LnLean.Wire.BigSize.decode_encode`) and
   still marked `statementOnly`.
5. Recommended merged set: D07 + E07's C8-necessity lemmas, D08 + E08's
   `decode_value_lt`, followed by catalog-name/status fixes in
   `Obligations.lean`, `Traceability.lean`, and the generated docs.
