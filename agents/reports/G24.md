### Statement fidelity

**Target 47.** BOLT 3 is explicit that the commitment output for a surviving HTLC is the *full* HTLC amount, and only the dust test subtracts the second-stage fee (`refs/bolts/03-transactions.md:339-349`). The worked example (`:539-551`) is decisive:

- offered 5000 sat, timeout fee 3315, dust 546 → output **5000** sat in the commitment tx;
- offered 1000 sat → trimmed, **1000** sat added to fee;
- received 7000 sat, success fee 3515 → output **7000** sat;
- received 800 sat → trimmed, **800** sat added to fee.

`D47` implements exactly this split: `waveD_d47_dustThreshold h d t s = d + secondStageFee …` and `waveD_d47_isDustOutput` tests the **gross** `h.amountSat` (`D47.lean:63-76`); `CommitmentHTLCOutput.ofHTLC` sets `amountSat := Msat.toSatFloor h.amountMsat`, i.e. the gross amount (`D47.lean:140-147`); `trimHtlcs` keeps the gross record and `buildCommitmentTrimmed` subtracts the whole pending value from `toRemoteSat` (`D47.lean:296-308`). Applied to the BOLT example it yields outputs 5000 + 7000 and trimmed value 1800, so effective fee = 5340 + 1800 = 7140, matching BOLT's stated actual fee.

`E47` instead uses `htlcOutputValue = floor(amount_msat/1000) - secondStageFee` as the **stored output value**: `htlcRecordOf` has `amountSat := htlcOutputValue h timeoutFee successFee` (`E47.lean:67-73`), and `buildTrimmedCommitment` emits those records and sets `feeSat = required + dustValue` (`E47.lean:348-365`). On the same example it produces outputs 1685 + 3485 and trimmed value 0, so its `feeSat` is 5340 rather than BOLT's 7140. It understates the two kept outputs by 3315 + 3515 = 6830 sat and the trimmed contribution by 1800 sat. `waveE_e47_live_value_split` is true only for this net-valued notion, not for the BOLT ledger.

The model's own constructor confirms the gross convention: `Commitment.addHtlc` tests `h.amountSat < dustLimitSat + htlcTxFeeSat` and appends `h` unchanged (`LnLean/Proofs/Channel/CommitmentTxProps.lean:271-277`). `E47`'s net-valued `amountSat` would be double-fee-reduced if fed to this API. `E47.md:66-68` claims its trimmed value "matches BOLT 3", but the module's `dustValue` is a sum of net values; the report is inconsistent with its own definition.

**Target 48.** BOLT 3 has three keys: value, then `scriptpubkey`, then `cltv_expiry` for HTLC outputs (`refs/bolts/03-transactions.md:54-59`). `CommitmentOutput` has only `toLocal/toRemote/htlc direction+valueSat/anchors` (`LnLean/Channel/Types.lean:197-203`), so the script key is not expressible; `CommitmentHTLCOutput` carries `cltvExpiry` (`Types.lean:183-188`) but `CommitmentOutput.htlc` drops it, so the third key is not expressible either. Both `D48` and `E48` say this explicitly and prove only the value key. `E48` additionally proves the faithful positive form: `waveE_e48_valueSortedOutputs := c.commitmentOutputs.mergeSort waveE_e48_valueLe`, `waveE_e48_valueSortedOutputs_perm`, `waveE_e48_valueSortedOutputs_ordered`, and `waveE_e48_exists_valueOrdered_perm` — an unconditional value-sorted permutation of the model's pre-sort list. `D48` stops at the negative/characterization side (`waveD_d48_valueSorted_iff_noAnchors`, two counterexamples) and does not construct the sorted view.

## Reasoning

For target 47 the files are not close once the value convention is checked. Declaration count (E47 53 vs D47 39) and the late green build are irrelevant: `E47` proves a theorem about a commitment whose HTLC outputs are all short by their second-stage fee and whose fee omits the gross trimmed amount. `E47`'s own BOLT quotation says the dust test subtracts the fee; it then wrongly reuses that post-fee quantity as the output value. On BOLT's published example the discrepancy is 6830 sat in kept outputs and 1800 sat in fee — exactly the kind of accounting error this obligation exists to rule out. `D47` gets the example right, matches `Commitment.addHtlc`'s gross-amount convention, proves the exact trim partition, and proves the BOLT ledger (`effectiveFee = fee + trimmedValue`) plus the precise reasons the existing constructors cannot derive it. `D47` is the whole-file version to keep. The only caveat is that `D47` should be combined with the liveness notion from `Channel.HTLC` at integration time if the catalog is later strengthened; that is a model refinement, not a reason to take `E47`.

For target 48 both files build and both are honest about the missing script/CLTV fields. `E48` is strictly more useful: it has the general negative theorem, a realistic balance counterexample, an unsorted-HTLC counterexample, the anchor cap theorems (`any non-anchor output ≤ 330`), the exact anchor-free characterization, and — decisively — the unconditional `mergeSort` sorted-permutation result that is the closest expressible rendition of BOLT 3's "Sort the outputs into BIP 69+CLTV order." `D48`'s characterization is correct but redundant with `E48`'s and lacks the positive construction. `E48` is the whole-file version to keep; `D48` is a valid fallback only if `E48` cannot be imported in the combined tree.

`F08`/`F09` do not change either verdict. `F08` is the more ambitious ordering hardening (an `OutputEntry` with CLTV and an abstract script rank, `bip69Sort`, `bip69Sort_sorted`, `bip69Sort_perm`), but it has never built and has no report, so it cannot be recommended over a green `E48`. `F09` is the dust hardening equivalent, but it is explicitly conditional and contains a `sorry` at `F09.lean:472`; `D47` already proves the same ledger unconditionally for its constructor and proves the impossible unconditional form as a counterexample instead of a `sorry`.
