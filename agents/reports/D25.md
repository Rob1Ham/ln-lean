- Theorems/definitions:
  - `MacInvalid I tag l` — definition: the verifier returns `false` for
    `tag` and the layer's HMAC. This is the model's only available notion
    of an invalid HMAC.
  - `MacAccepted I tag l` — definition: the verifier returns `true`.
  - `waveD_d25_macInvalid_iff_not_accepted` — the two predicates are
    complementary.
  - `waveD_d25_hmac_sound` — a successful `openLayer` (the checked peel,
    and the only path that yields a hop to forward) entails a layer with
    the returned hop whose HMAC the verifier accepted, and that the
    returned packet is the original layer list's tail. This is the
    mechanical half of the catalog target
    `LnLean.Routing.Onion.hmac_sound`.
  - `waveD_d25_invalid_hmac_rejected` — if the head layer's HMAC is
    rejected, `openLayer` returns `none`.
  - `waveD_d25_no_forward_of_invalid` — under the same hypothesis no
    hop/next pair is returned, so no forward instruction exists on the
    checked path.
  - `waveD_d25_openLayer_forward_iff_accepted` — for a non-empty packet,
    a forward result exists exactly when the verifier accepts the head
    layer. Rejection and forwarding are complementary outcomes.
  - `waveD_d25_openLayer_accepted` — positive direction: accepted HMAC
    yields exactly the head hop and the inner packet.
  - `VerifierRejectsWrongTag I tag layers` — definition: the verifier
    rejects every layer tag different from the expected tag (the concrete
    verifier-binding shape of C8 `hmacBinding`).
  - `waveD_d25_wrong_tag_rejected` — conditional: a head layer carrying a
    tag different from the expected tag, under a verifier that rejects
    wrong tags, is rejected.
  - `waveD_d25_accepted_tag_eq` — conditional contrapositive: under that
    verifier, any forwarded layer carries exactly the expected tag.
  - `rejectingInterface`, `sampleHop`, `samplePacket` — concrete data for
    the counterexample.
  - `waveD_d25_peel_bypasses_hmac` — mechanized counterexample: with an
    always-rejecting verifier, `openLayer` returns `none` while the
    structural `peel` still returns `some (.forward sampleHop next)`.
    Hence the rejection guarantee belongs to `openLayer`, not `peel`.

- Statement fidelity: the catalog target names
  `LnLean.Routing.Onion.hmac_sound`, which is not a declaration in the

  `Traceability.lean`). The model has no predicate separating an
  "authentic" HMAC from a verifier-accepted one, so the faithful

  not call `openLayer`; the counterexample records that a forwarding
  implementation must use the checked path. No claim is weakened silently.

## Remaining gap / next step

HMAC unforgeability / verifier soundness (C8, `OnionInterface.hmacBinding`)
is not proved, and the model gives no way to derive it: `hmacBinding` is an
uninterpreted `Prop` with no elimination principle, and there is no
`MacValid` field or keyed-hash model in `LnLean.Routing.Onion`. The
mechanical rejection property is complete for `openLayer`; closing the
cryptographic gap would require a model-level `MacValid` predicate plus an
assumption `verifyHmac tag l.hmac = true → MacValid tag l`, or the C8
verifier-binding statement `l.hmac ≠ tag → verifyHmac tag l.hmac = false`.
Also note that `peel` can forward an unauthenticated layer if called
directly; the model does not enforce that implementations enter through
`openLayer`.
