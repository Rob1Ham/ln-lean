# F05 — Gossip announced-key admission

## Target
- Marker: `LN-WF-F05`
- Module: `LnLean.Proofs.ModelHardening.F05`

## Result
- Status: counterexample (the faithful unconditional claim is false; the
  admitted-step positive theorem and an exact characterization are proved)
- Build: RC 0
- New definitions:
  - `UpdateKeyAnnounced (s : GossipState) (u : ChannelUpdate) : Prop` — some
    stored `channel_announcement` for `u.shortChannelId` announces
    `u.signingKey` as `nodeKey1` or `nodeKey2`.
  - `UpdateKeyAdmissible (verify : SigVerifier) (s : GossipState)
    (u : ChannelUpdate) : Prop` — the stronger form that also requires the
    backing announcement's four BOLT 7 signatures to verify.
  - `admitChannelUpdate (verify : SigVerifier) (s : GossipState)
    (u : ChannelUpdate) : GossipState` — accepts only when
    `UpdateKeyAnnounced s u` holds and `u.signatureValid verify` holds, then
    applies wave A's timestamp replacement rule.
- Main theorems:
  - `updateKeyAdmissible_implies_announced`
  - `admitChannelUpdate_rejects_unannounced`
  - `admitChannelUpdate_change_requires_key`
  - `admitChannelUpdate_change_requires_signature`
  - `admitChannelUpdate_change_requires_newer`
  - `admitChannelUpdate_sound`
  - `admitChannelUpdate_changes_of_conditions`
  - `admitChannelUpdate_change_iff` — a change occurs iff the key is
    announced, the signature verifies, and the timestamp is strictly newer.
  - `admitChannelUpdate_updates_of_change`
  - `admitChannelUpdate_eq_acceptChannelUpdate_of_announced` — the key check
    is the only extra gate relative to `acceptChannelUpdate`.
  - `admitChannelUpdate_announcements`
  - `updateKeyAnnounced_admitChannelUpdate`
  - `admitChannelUpdate_change_key_announced_after`
  - `waveF_f05_unannounced_key_counterexample` — empty store, an
    always-accepting verifier, and an update with an empty key; the un-gated
    `acceptChannelUpdate` changes the store while `UpdateKeyAnnounced` fails.
  - `waveF_f05_admission_rejects_unannounced_key` — the same update is
    rejected by `admitChannelUpdate`.
  - `waveF_f05_accepted_update_key_announced` — the faithful unconditional
    statement, retained with one `sorry` and the `LN-WF-F05` marker.
- Added hypotheses: the positive theorem is conditional on the explicit
  admission predicate `UpdateKeyAnnounced s u`, plus the existing
  `signatureValid` and strictly-newer-timestamp conditions.  No
  cryptographic unforgeability is assumed.
- Statement fidelity: the predicate is the same either-announced-key
  relation that wave A records as the open obligation `LN-GOSSIP-001`
  (`GossipProps.updateKeyAnnounced`): BOLT 7 says the `channel_update`
  must be signed by the `node_id` from the matching
  `channel_announcement`.  The unconditional statement is not weakened; it
  is kept verbatim with one `sorry`, and the mechanized counterexample
  proves it false for the current model.

## Missing model field / next step

Wave A stores `ChannelUpdate.signingKey` as an independent `PubKey` field
and `GossipState.applyUpdate` / `GossipProps.acceptChannelUpdate` never
look it up in `GossipState.announcements`.  Closing `LN-GOSSIP-KEY`
therefore requires a model change, not a larger proof:

1. Key the announcement lookup by `(short_channel_id, direction)` using
   BOLT 7 `channel_flags` bit 0, and require the update to be signed by the
   `node_id` for that direction (currently either announced key is
   accepted).
2. Prefer removing `signingKey` from `ChannelUpdate` and deriving the
   verification key from the store, so an unannounced key is unrepresentable
   rather than merely rejected by an admission check.
3. Optionally fold `UpdateKeyAdmissible` into the admission path so only
   announcements with valid four-way signatures can supply a key.
