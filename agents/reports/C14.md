## 3. Proof approach and helpers

I read `LnLean/Routing/Gossip.lean`, `LnLean/Routing/Graph.lean`, and the
relevant wave-A definitions before proving.  The key definitions are:

* `SigVerifier := PubKey → ByteArray → GossipSignature → Bool` is an
  unconstrained function parameter.
* `signatureValid verify key digest sig := verify key digest sig = true`;
  nothing relates a successful check to `GossipSignature.Valid`
  (`bytes.size = 64`).
* `GossipState.applyUpdate` only compares
  `s.latestUpdateTimestamp < u.timestamp`.  It never inspects
  `signingKey`, `shortChannelId`, or the announcement list.
* `acceptChannelUpdate verify s u` is `if u.signatureValid verify then
  s.applyUpdate u else s`.
* `bindChannel verify a` is `if a.signaturesValid verify then some { ...,
  capacitySat := a.capacitySat } else none`; `capacitySat` is an
  unconstrained `Nat`.
* `ChannelUpdate.signingKey` and `ChannelAnnellation.nodeKey1/2` are
  independent fields.

Rather than fabricating a proof of a false claim, I mechanised the
counterexamples.  `acceptingVerifier_changes_empty` first establishes that the
acceptance hypothesis is non-vacuous (the update is newer than the empty
store's clock and the verifier accepts it).  Each counterexample theorem is a
direct instantiation and uses only `simp`; there is no large tactic and no new
axiom/assumption.  The counterexamples are `private` so the public theorem
surface is unchanged.

## 4. False/unprovable statements and missing model fields

All three obligations are **false for the current wave-A model**, not merely
hard.  They are therefore retained as `sorry` + `-- OBLIGATION:` per the
wave-C rule; they are not closed by a proof of the stated claim.

### LN-GOSSIP-001 — signing-key attribution

Counterexample (`LN_GOSSIP_001_counterexample`):

* `s = emptyGossipState = ⟨[], [], []⟩`, so `s.announcements = []`.
* `u = unannouncedUpdate`, with `timestamp = 1`, and
  `verify = acceptingVerifier`.
* `s.latestUpdateTimestamp = 0 < 1`, so `s.applyUpdate u` inserts `u`;
  `acceptChannelUpdate` therefore changes the store.
* No announcement exists, so the required existential
  `∃ a ∈ s.announcements, ...` is false.

Missing model field / link: nothing connects `ChannelUpdate.signingKey` to
`ChannelAnnellation.nodeKey1` or `nodeKey2`.  BOLT 7 takes the verification key
from the matching `channel_announcement` (`refs/bolts/07-routing-gossip.md:544`),
using the `direction` bit; wave A's `GossipState.applyUpdate` has no channel
lookup at all.

### LN-GOSSIP-002 — positive capacity

Counterexample (`LN_GOSSIP_002_counterexample`):

* `a` has `capacitySat = 0`, and all four signature predicates are satisfied
  by `acceptingVerifier`.
* `bindChannel acceptingVerifier a = some b` with `b.capacitySat = 0`.
* Hence `0 < b.capacitySat` is false.

Missing model field / invariant: `ChannelAnnellation.capacitySat : Nat` has no
positivity invariant, and `bindChannel` does not check it.  BOLT 7 defines
`capacity` as the funding output value; the wave-A model does not relate it to
the L1 funding output (see the module docstring).

### LN-GOSSIP-003 — 64-byte signature

Counterexample (`LN_GOSSIP_003_counterexample`):

* `u = unannouncedUpdate` has `signature = ⟨ByteArray.empty⟩`, so
  `u.signature.bytes.size = 0`, not `64`.
* `acceptingVerifier` accepts it, and its timestamp is newer than the empty
  store, so `acceptChannelUpdate` changes the store.
* Hence the conclusion `u.signature.Valid` is false.

Missing model field / admission check: `GossipSignature.Valid` exists but
`SigVerifier` does not require it.  A production admission path must check
`u.signature.Valid` (BOLT 7 signature fields are 64 bytes) before accepting.

### Why the obvious definitional "fixes" were not applied

The wave-C rules require theorem statements to be kept exactly and prohibit
disguising a model gap as a proof.  Adding a guard inside the owned
definitions would make the obligations true only by changing their subject:

* Adding `u.signature.Valid` to `acceptChannelUpdate` would make
  LN-GOSSIP-003 immediate, but `applyGossipChecked_update_eq` is stated under
  only `u.signatureValid verify`; the equality would then be false, and its
  statement may not be changed.
* Adding an announcement/key-membership guard to `acceptChannelUpdate` for
  LN-GOSSIP-001 would break the same `applyGossipChecked_update_eq` proof and
  more.
* Adding a positivity check to `bindChannel` for LN-GOSSIP-002 would silently
  turn a missing admission invariant into a definitional guard, contrary to
  the "keep the original `sorry` + marker and document the model gap" rule.

These are integrator decisions, because they change model semantics used by
theorems in this file.
