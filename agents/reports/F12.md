# F12 — Reestablish no-rollback

## Result

- `sorry`/`axiom`/`admit`/`native_decide`/`unsafe`: none

### New definitions
- `RollsBack sent r`: a report names a commitment or revocation number
  strictly behind the last-sent counters.
- `NoRollback sent r`: the missing invariant; neither reported counter is
  behind the last-sent counter.  `not_rollsBack_iff_noRollback` and
  `rollsBack_iff_not_noRollback` prove it is the exact negation of
  `RollsBack`.
- `RetransmitTrace a b`: a reconnection interval of re-sending retained
  messages and receiving the peer's `channel_reestablish`.
- `ChannelActivity a b`: all sends and receipts on a `ChannelRecord`.
- `reportFields`, `adoptReported`, `adoptGuarded`: the peer report as
  `ReestablishFields`, a consumer that copies the report into the record
  (not what the model does), and the invariant-guarded consumer.
- Sample witnesses `sampleLedger`, `sampleRecord`, `staleReport`,
  `samplePeer`, `staleMessage`.
- `decidableNoRollback`: the invariant is decidable.

### Main theorems
- `noRollback_afterCommitment`, `noRollback_afterRevocation`,
  `noRollback_advanceReceived`: the invariant is preserved by every model
  counter advancement.
- `accepted_noRollback`, `accepted_not_rollsBack`: BOLT 2's
  `ReestablishAccepted` window (`lastSent ≤ reported ≤ lastSent + 1`)
  implies the invariant.
- `receive_channelReestablish_noRollback`: an accepted
  `channel_reestablish` leaves the addressed record's counters exactly
  unchanged, hence preserves the invariant.
- `receive_noRollback`: every accepted channel-directed receipt preserves
  the invariant, because `advanceReceived` is monotone in both counters.
- `retransmitTrace_counters_eq`: during a reconnection interval both counters
  are exactly constant.
- `retransmitTrace_noRollback`: retransmission cannot roll back acknowledged
  state; the counters do not move at all.
- `channelActivity_counters_monotone`: the unconditional model fact — no
  sequence of sends/receipts lowers either reported counter.
- `channelActivity_noRollback`: consequently no activity crosses the
  last-sent floor.
- `adoptReported_rollsBack`: mechanized rollback counterexample.  Adopting
  the stale report `(1, 0)` over a channel at `(4, 3)` against a ledger at
  `(3, 2)` moves the commitment counter from 4 back to 1.
- `adoptGuarded_noRollback`: the guard restores the invariant; guarded
  adoption never crosses the floor.
- `adoptGuarded_commitment_rewind_at_most_one` and
  `adoptGuarded_revocation_rewind_at_most_one`: inside the BOLT window the
  only permitted rewind is the single unacknowledged message (one counter
  step).
- `receive_accepts_stale_report`: the model's `receive` accepts the stale
  report because it never consults the invariant.  The report is discarded,
  so local state does not move; the rollback appears only in a consumer that
  adopts it (`adoptReported_rollsBack`).

### Added hypotheses
- `NoRollback sent r` (or `NoRollback sent c.reestablish`) in the
  invariant-preservation and guarded-adoption theorems.
- `c.reestablish.nextCommitmentNumber ≤ sent.lastCommitmentNumber + 1`
  (respectively revocation) in the "rewind at most one" theorems.
- `ReestablishAccepted sent r` in `accepted_noRollback`; this predicate
  already exists in `ChannelReestablishProps` and is not an added assumption
  to the model.
- `receive s m = some s'`, `findChannel s cid = some c`, and the transport
  equation are explicit facts about the model operation, as in the imported
  receipt lemmas.

### Statement fidelity
- **No silent weakening.**  The model-level no-rollback statement is
  unconditional: `channelActivity_counters_monotone` proves neither counter
  ever decreases, and `receive_channelReestablish_noRollback` proves the
  reestablish receipt is exactly counter-preserving.  The invariant is
  needed only for the *consumer* that would adopt the peer's report; the
  counterexample proves that need.
- `SentCounters.lastCommitmentNumber` is the last *sent* counter, not the
  last acknowledged one.  This is deliberate: BOLT 2 permits equality (the
  last message was lost and is retransmitted) and forbids anything smaller.
  The "rewind at most one" theorems separate that one-message allowance from
  rollback of acknowledged state.
- **Not mechanized:** the "retransmits unacknowledged updates" half of
  `LN-PR-005`.  `Msg.commitment_signed` carries no commitment number,
  `ChannelRecord.recordSent` overwrites the retained copy unconditionally,
  and `resend` is an explicit operation.  The module therefore proves the
  no-rollback half and mechanizes the missing guard rather than claiming the
  retransmission half.
- The file is self-contained: it imports only `LnLean.Protocol.Peer`,
  `LnLean.Protocol.Messages`, and
  `LnLean.Proofs.Protocol.ChannelReestablishProps`; it imports no other
  Wave-F module and edits no model file.

## Missing model field / next step
- `PeerState.receive` has no `SentCounters` parameter and no error/close
  result.  A production version should reject a report failing
  `ReestablishAccepted`/`NoRollback`; the model only has `ReestablishRejected`
  as a proposition, so acceptance cannot change the transition.
- `ChannelRecord` should store the peer's reported counters (or the last
  accepted report) so the invariant can be maintained as a state invariant,
  not only checked by a consumer.
- `commitment_signed` needs a commitment number for duplicate/stale detection;
  currently `advanceReceived` advances on every receipt, which is an
  over-advance (not a rollback).
- Next integration step: thread `NoRollback` through `receive` and connect
  it to the `Channel` view via `countersOf`, so the theorem covers
  `localCommitmentNumber` / `remoteCommitmentNumber` as well.
