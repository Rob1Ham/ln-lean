# E48 — commitment output ordering

## Target

- Parent/catalog: `LN-CH-003`
- Module: `LnLean.Proofs.WaveE.E48`
- File: `LnLean/Proofs/WaveE/E48.lean`
- Obligation marker: `-- OBLIGATION: LN-WE-E48`

Catalog claim: "Commitment outputs are ordered by value then script, and dust
HTLCs are trimmed."  BOLT 3 §*Transaction Output Ordering* at the pinned BOLT
commit `1aadb719…`: value smallest first, then `scriptpubkey` (memcmp on the
common prefix, shorter first), then `cltv_expiry` for HTLC outputs; the
construction section says "Sort the outputs into BIP 69+CLTV order."

## Result

- Status: **counterexample** (the claim, read as a property of the model's
  output list, is false; the full BOLT 3 rule is also *not expressible* in the
  current model).
- Build: RC 0 —
  `flock -w 900 /tmp/ln-build.lock lake build LnLean.Proofs.WaveE.E48`
  (Lean `v4.35.0` on the brief's PATH).  No `sorry`, no `axiom`, no
  `native_decide`, no Mathlib.
- Theorems/definitions (all named `waveE_e48_*`):
  - `ValueOrdered` — BOLT 3's first key: `Pairwise (fun a b => value a ≤ value b)`.
  - `waveE_e48_htlcSegment`, `waveE_e48_anchorSegment`,
    `waveE_e48_commitmentOutputs_decompose`, `waveE_e48_commitmentOutputs_cons`,
    `waveE_e48_anchors_suffix` — the order the model *actually* implements:
    `to_local ++ to_remote ++ HTLCs-in-channel-list-order ++ anchors`, with the
    two anchors last.
  - `waveE_e48_htlcSegment_values` — HTLC block values are the `amountSat`s in
    the same channel order (no sort is performed).
  - Negative results:
    `waveE_e48_not_valueOrdered_of_toLocal_gt_toRemote`,
    `waveE_e48_counterexample_balances*` (concrete `to_local = 1000`,
      `to_remote = 500` → output list `[to_local 1000, to_remote 500]`),
    `waveE_e48_counterexample_htlc_order*` (HTLC amounts `[1000, 500]`),
    `waveE_e48_valueOrdered_before_anchor` (anchors last ⇒ any non-anchor
      output ≤ 330 sat), `waveE_e48_valueOrdered_toRemote_le_anchor`,
    `waveE_e48_valueOrdered_htlc_le_anchor`,
    `waveE_e48_not_valueOrdered_of_anchor_lt_toRemote`.
  - Exact characterization (no anchors):
    `waveE_e48_valueOrdered_iff_model_order`:
    `ValueOrdered c.commitmentOutputs ↔ toLocal ≤ toRemote ∧
     (∀ v ∈ HTLC amounts, toRemote ≤ v) ∧ HTLC amounts pairwise non-decreasing`;
    assembled from `waveE_e48_valueOrdered_toLocal_le_toRemote`,
    `..._toRemote_le_htlc`, `..._htlc_pairwise`,
    `waveE_e48_valueOrdered_of_model_order`.
  - Positive BOLT 3-shaped result (unconditional):
    `waveE_e48_valueLe`, `waveE_e48_valueSortedOutputs`,
    `waveE_e48_valueSortedOutputs_perm`,
    `waveE_e48_valueSortedOutputs_ordered`,
    `waveE_e48_exists_valueOrdered_perm` —
    `∃ l, l.Perm c.commitmentOutputs ∧ ValueOrdered l`, explicitly witnessed by
    `List.mergeSort` on the value key; `..._mem_iff` records that the sorted
    view preserves membership/counts.
- Added hypotheses (documented, not silent weakenings):
  - `hl : c.toLocalSat ≠ 0`, `hr : c.toRemoteSat ≠ 0` where the model's heads
    must be identified (zero-valued outputs are trimmed to `[]`).
  - `ha : c.anchorOutputs = false` for the `iff` characterization; with
    anchors the fixed order cannot be value-ordered except in dust-only
    commitments (proved as the 330-sat cap theorems).
- Statement fidelity:
  - `LnLean.Channel.Commitment.commitmentOutputs` is a pre-sort concatenation
    and is **not** value-ordered in general, so the catalog statement as a
    property of the model list is false (mechanized counterexamples).
  - The BOLT 3 ordering is a property of the *sorted* transaction; the model
    does not build that view, hence the `valueSortedOutputs` construction and
    the permutation/ordering theorems are the faithful positive rendition.
  - Note: the model's docstring in `Channel/Commitment.lean` says the list is
    "in BOLT 3 order: to_local, to_remote, HTLC outputs, then anchors"; per the
    pinned BOLT text that fixed order is *not* BOLT 3 order (BOLT 3 sorts).

## Remaining gap / next step

The two missing model fields that prevent stating the full BOLT 3 rule:

1. `CommitmentOutput` has **no `scriptPubKey`** field, so the second key
   ("then script", memcmp on the common prefix) cannot be stated.
2. `CommitmentOutput.htlc` keeps only `direction` and `valueSat`; it drops
   the HTLC's `cltvExpiry` (and `paymentHash`), so the third key ("increasing
   `cltv_expiry`") cannot be stated either.

Next step: extend `CommitmentOutput` with a script key (and `cltvExpiry` on the
HTLC constructor), define the lexicographic BIP 69+CLTV key, and prove
`mergeSort` on that key is a permutation of `commitmentOutputs` and yields the
unique BOLT 3 order; then the catalog entry can be upgraded from
"value half only" to the full claim.  The model's `commitmentOutputs`
docstring should also stop calling the unsorted fixed order "BOLT 3 order".
