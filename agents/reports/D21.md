# D21 — channel_reestablish retransmits unacknowledged updates without rolling state back.

## Target

- Parent/catalog: `LN-PR-005`
- Module: `LnLean.Proofs.WaveD.D21`
- File: `LnLean/Proofs/WaveD/D21.lean`

## Result

- Status: conditional (positive laws proved; mechanized counterexample for the handshake-retransmittable kinds)
- Build: RC 0 (`export PATH=/dev/shm/btc/elan/toolchains/leanprover--lean4---v4.35.0/bin:$PATH; flock -w 900 /tmp/ln-build.lock lake build LnLean.Proofs.WaveD.D21`)
- Theorems/definitions:
  - `retransmittableKind` — BOLT 2's five retransmittable kinds
    (`funding_signed`, `channel_ready`, `commitment_signed`, `revoke_and_ack`,
    `shutdown`) as a decidable tag predicate.
  - `channelId_recordSent`, `channelId_advanceReceived`,
    `lastSent_recordSent`, `lastSent_advanceReceived` — record-level frame
    laws: sending/receiving keeps the channel id, records the sent message,
    and never discards a retained copy.
  - `advanceReceived_commitment_monotone`,
    `advanceReceived_revocation_monotone`, `advanceReceived_consistent` —
    receiving never decreases either counter and preserves
    `next_revocation_number ≤ next_commitment_number`.
  - `findChannel_pred`, `findChannel_updateChannel_self` — locator lemmas
    bridging `updateChannel` to `resend`/`findChannel` (beware duplicate
    channel ids: `updateChannel` rewrites every matching entry, the lemmas
    only claim the first found entry).
  - `waveD_d21_send_channel_step` — a successful non-handshake,
    channel-directed `send` makes the addressed channel exactly
    `c.recordSent m`.
  - `waveD_d21_receive_channel_step` — a successful non-handshake,
    channel-directed `receive` makes the addressed channel exactly
    `c.advanceReceived m`.
  - `waveD_d21_resend_after_send` — for a retransmittable
    non-handshake kind, `resend` after a successful send returns the sent
    message.
  - `waveD_d21_receive_no_rollback` — a receive never decreases the
    commitment counter, never decreases the revocation counter, never
    changes any `lastSent` slot, and preserves counter consistency.
  - `waveD_d21_receive_reestablish_channel` — receiving
    `channel_reestablish` is the identity on the addressed channel.
  - `waveD_d21_reestablish_retransmits` — composed claim: send a
    retransmittable update, then receive `channel_reestablish` for that
    channel; `resend` still returns the update (and no counter moved back).
  - `waveD_d21_send_handshake_channels`,
    `waveD_d21_resend_unchanged_by_handshake_send` — a handshake send
    leaves the channel list (and hence `resend`) untouched.
  - `waveD_d21_handshake_retransmission_gap` — counterexample: there is a
    peer state in which a legal `funding_signed` send succeeds but
    `resend … .fundingSigned = none`.
- Added hypotheses:
  - The step/resend theorems assume the message is non-handshake
    (`sendEvent? m = none` / `receiveEvent? m = none`), is channel-directed
    (`channelId? m = some cid`), and that the addressed channel is found in
    the pre-state (`findChannel s cid = some c`).  These are exactly the
    branches of `send`/`receive`; the same-state post-state channel is then
    supplied as `hfc'`, which the model guarantees but which is easiest to
    pass explicitly because `findChannel` is a `List.find?`.
  - `waveD_d21_reestablish_retransmits` additionally assumes the
    `channel_reestablish` names the same channel as the update
    (`re.channelId = cid`).
  - No counter bound (`< 2^48`), no `wellFormed`, and no authentication
    hypothesis is used or needed.
- Statement fidelity: the catalog target
  `LnLean.Protocol.Peer.reestablish_no_rollback` is statement-only; there is
  no such constant in the model.  This module proves the faithful model-level
  content: the `channel_reestablish` counters are monotone under every
  modelled receive, the retained last-sent copies survive every receive, and
  `resend` returns a message that was actually sent for
  `commitment_signed` / `revoke_and_ack` / `shutdown`.

  Two model limitations are reflected literally, not hidden:
  1. there is no per-update acknowledgement ledger, so “unacknowledged” is
     represented only by “last retained copy of that kind”; the theorems
     therefore cannot distinguish acknowledged from unacknowledged updates;
  2. `send` dispatches `funding_signed` and `channel_ready` through
     `handshakeStep` before reaching `ChannelRecord.recordSent`, so those
     two kinds are never retained.  `waveD_d21_handshake_retransmission_gap`
     mechanizes this: for `funding_signed` a legal send leaves
     `resend = none`.  The same applies to `channel_ready` by the general
     `waveD_d21_send_handshake_channels` lemma.

## Remaining gap / next step

- Model gap: `ChannelRecord.recordSent` already knows how to store
  `funding_signed` and `channel_ready`, but `PeerState.send` routes those
  kinds to `handshakeStep` and never calls `recordSent`.  A model fix
  (outside this agent's ownership) would record the outbound message before
  the handshake branch, or record it in the handshake branch for the
  `sendFundingSigned` / `sendChannelReady` events.  After that,
  `waveD_d21_resend_after_send` extends to all five retransmittable kinds.
- Model gap: no acknowledgement ledger, so the stronger BOLT 2 property
  (“only messages the peer has not acknowledged are retransmitted”) cannot
  be stated.  Adding `ackedCommitment`/`ackedRevocation` counters plus a
  `retransmit` operation would be the next faithful step.
- The duplicate-channel-id behaviour of `updateChannel` (rewrites all
  matching entries) is not constrained by the locator lemmas; a channel-id
  uniqueness invariant would let `findChannel`/`resend` be fully extensional.
