### Added hypotheses

1. Global form: `LiveIdsDistinct hs`.  This is precisely the channel invariant
   the record model does not maintain.
2. Per-direction form: `DirIdsDistinct dir hs`.  This is the invariant actually
   guaranteed by BOLT 2's counter rule.
3. Counter model: `HtlcBook.Inv b` = `counterFresh b` (every live id is below
   its sender's counter) together with `DirIdsDistinct .local b.htlcs` and
   `DirIdsDistinct .remote b.htlcs`.

### Statement fidelity

The exact unconditional claim is **not** a theorem of `LnLean.Channel.HTLC`.
The model's `addHTLC` (`LnLean/Channel/HTLC.lean:224`) takes `id : Nat` as a
caller-supplied argument and has no access to the channel's live set or to an
id counter, so it cannot reject a repeated id.  `waveD_d16_addHTLC_allows_duplicate_id`
and `waveD_d16_id_unique_counterexample` mechanize this gap.

The claim is also too strong *globally* even under BOLT 2: `02-peer-protocol.md:2838-2843`
says "for the first HTLC it offers: MUST set `id` to 0.  MUST increase the
value of `id` by 1 for each successive offer", and rust-lightning realizes
this with two independent counters, `next_holder_htlc_id` and
`next_counterparty_htlc_id` (`lightning/src/ln/channel.rs:3719-3720`; receipt
check at `:8392`, local increment at `:14670-14682`).  Both counters start at
0, so id 0 may legitimately exist once in each direction
(`waveD_d16_bolt_allows_cross_direction_duplicate`).  Thus the BOLT-faithful
statement is the per-direction one (`waveD_d16_dir_id_unique`); the global form
needs an additional cross-direction disjointness assumption, which the catalog
does not state.

No claim was weakened silently: the global theorem carries `LiveIdsDistinct`
as an explicit hypothesis, and the counterexamples show why no unconditional
version exists in the current model.

## Remaining gap / next step

The missing model field is a channel-level pair of BOLT 2 id counters (and the
associated id-assignment/freshness guard on add).  The proof-level `HtlcBook`
above supplies them and proves invariant preservation.  To close the gap in
the model itself:

1. add `nextHolderHtlcId` / `nextCounterpartyHtlcId` to a channel state record;
2. make `addHTLC` allocate the id from the appropriate counter and increment
   it (rather than accepting a raw `Nat`);
3. prove by induction over the channel transition relation that
   `HtlcBook.Inv` holds initially and is preserved, then derive the per-direction
   uniqueness corollary.

Also out of scope: BOLT 2's reconnection rule ("MUST ignore a repeated `id`
value after a reconnection") and 64-bit counter wrap; neither is modelled here.
