# D17 — open_channel accepts a funding amount only above the dust and minimum-channel bounds.

## Target

- Parent/catalog: `LN-PR-001`
- Module: `LnLean.Proofs.WaveD.D17`
- File: `LnLean/Proofs/WaveD/D17.lean`

## Result

- Status: proved
- Build: RC 0
  (`export PATH=/dev/shm/btc/elan/toolchains/leanprover--lean4---v4.35.0/bin:$PATH; flock -w 900 /tmp/ln-build.lock lake build LnLean.Proofs.WaveD.D17`)
- Theorems/definitions:
  - Model: `OpenChannelMsg`, `AcceptPolicy`, `OpenChannelAcceptance`,
    `OpenChannelMsg.dustBound`, `OpenChannelMsg.minChannelBound`,
    `OpenChannelMsg.policyMinBound`, `OpenChannelMsg.accepts`,
    `acceptOpenChannel`; constants `minChannelValueSatoshis = 1000`,
    `minDustLimitSatoshis = 354`, `totalBitcoinSupplySatoshis`,
    `largeChannelThresholdSatoshis = 2^24`.
  - Main result: `waveD_d17_open_bounds` — if
    `acceptOpenChannel p m = some a`, then
    `m.dustLimitSatoshis < m.fundingSatoshis`,
    `minChannelValueSatoshis ≤ m.fundingSatoshis`, and
    `p.minFundingSatoshis ≤ m.fundingSatoshis`.
  - Corollaries: `waveD_d17_accept_funding_above_dust`,
    `waveD_d17_accept_funding_at_least_min_channel`,
    `waveD_d17_accept_funding_at_least_policy_min`,
    `waveD_d17_accept_reserve_at_least_dust`.
  - Rejection directions: `waveD_d17_reject_of_funding_le_dust`,
    `waveD_d17_reject_of_funding_below_min_channel`,
    `waveD_d17_reject_of_funding_below_policy_min`.
  - Non-vacuity: `waveD_d17_example_accepted`,
    `waveD_d17_example_dust_rejected`,
    `waveD_d17_example_below_min_rejected`.
  - No `sorry`, `axiom`, `admit`, `native_decide`, `unsafe`, or Mathlib.
- Added hypotheses: none inside the theorems. The local acceptor model adds
  the BOLT 2/LDK fields needed to state the claim: `fundingSatoshis`,
  `pushMsat`, `dustLimitSatoshis`, `channelReserveSatoshis`, plus the
  acceptor policy fields `minFundingSatoshis` and `supportsLargeChannel`.
  The policy minimum is a parameter, not a fixed constant.
- Statement fidelity:
  - The committed wave-A model has no `open_channel` message and no funding
    amount. `LnLean/Protocol/Handshake.lean:52-55` and
    `LnLean/Protocol/Messages.lean:56-61` record that `open_channel` is
    absorbed into `HandshakeState.canSendAccept`; consequently the catalog
    target `LnLean.Protocol.Handshake.open_bounds` does not exist. This
    module therefore states and proves the faithful unconditional form in a
    new local acceptor model; it does not modify or reinterpret any committed
    model file.
  - The model follows BOLT 2 §The `open_channel` Message
    (`refs/bolts/02-peer-protocol.md:680-890`): `push_msat ≤
    1000 * funding_satoshis` (`:808`), `354 ≤ dust_limit_satoshis ≤
    channel_reserve_satoshis` (`:869-870`), and the `2^24` large-channel
    threshold (`:805-808`, `:873`). It follows LDK
    (`lightning/src/ln/channel.rs:4182,4198,4209,4267,4308`) for the
    1000-satoshi hard minimum, the total-supply upper bound, the reserve
    bound, and the `min_funding_satoshis` policy.
  - The dust condition is strict (`dust_limit_satoshis <
    funding_satoshis`), matching the claim's "above the dust ... bound".
    LDK's literal check at `channel.rs:4209` is the weaker
    `dust_limit_satoshis ≤ channel_value_satoshis`; the strict policy is
    stated explicitly in `OpenChannelMsg.accepts`.
  - The minimum-channel condition has two independent bounds: LDK's hard
    `MIN_CHANNEL_VALUE_SATOSHIS = 1000` (`channel.rs:1031`) and the
    acceptor's configurable `minFundingSatoshis`
    (`channel.rs:4267`). Both are proved.
  - The witnesses show the predicate is not vacuous: a 100000-sat opening is
    accepted, an opening whose funding equals its dust limit is rejected,
    and a 999-sat opening is rejected.

## Remaining gap / next step

The catalog row remains a local-model theorem until the scaffold gains an
`open_channel` constructor or a funding-amount field in the handshake state.
Such a field would let `Handshake.open_bounds` be stated against the actual
`HandshakeStep`/`Reachable` relation instead of the local acceptor record.
No change to this module is needed for that integration: `acceptOpenChannel`
and `OpenChannelMsg.accepts` can be used as the guard on a future
`recvOpenChannel` event.
