# E31 — A keysend payment uses the sender-supplied preimage as the payment preimage.

## Target

- Parent/catalog: `LN-PM-006`
- Module: `LnLean.Proofs.WaveE.E31`

## Result

- Status: proved (operational form); uniqueness form conditional on collision-freeness
- Build: RC 0
  `flock -w 900 /tmp/ln-build.lock lake build LnLean.Proofs.WaveE.E31`
- Theorems/definitions:
  - `waveE_e31_sender_preimage_commits` — a valid keysend's stored preimage hashes to `session.paymentHash`.
  - `waveE_e31_preimage_commits` — the same fact in the wave-A `PaymentSession.preimageCommits` relation.
  - `waveE_e31_reveal_is_sender_preimage` — every preimage revealed along any settlement trace equals `k.preimage`.
  - `waveE_e31_reveal_is_payment_preimage` — every revealed value equals the sender preimage and hashes to the payment hash.
  - `waveE_e31_success_reveals_sender_preimage` — a pending keysend settled successfully reveals exactly `some k.preimage`.
  - `waveE_e31_successful_payment_uses_sender_preimage` — combines the success reveal with the hash commitment.
  - `waveE_e31_preimage_unique_of_collision_free` — conditional: under `CollisionFree sha256`, any preimage matching the payment hash equals the sender's.
  - `waveE_e31_preimage_binding_of_collision_free` — trace form of the conditional uniqueness result.
  - `waveE_e31_preimage_binding` — unconditional operational law: hash commitment plus sender-preimage identity for every revealed value.
  - `waveE_e31_preimage_binding_not_unconditional` — mechanized counterexample (constant hash) showing uniqueness cannot be unconditional.
  - `LnLean.Payment.Keysend.preimage_binding` — the exact catalog target name, proved from `waveE_e31_preimage_binding`.
- Added hypotheses:
  - None for the operational claim (hash commitment, revealed-preimage identity, successful reveal).
  - `CollisionFree sha256` (the payment layer's idealised C1, `LnLean.Payment.CollisionFree`) is required only for uniqueness among *arbitrary candidate* preimages.
- Statement fidelity:
  - The model's `Keysend.Valid sha256` is exactly the recipient's keysend check
    `payment_hash = sha256(preimage)` (LDK `InvalidKeysendPreimage`).
  - `revealedPreimage` returns `some k.preimage` iff the session succeeded, so the
    operational claim is unconditional: the recipient fulfils with the value carried in
    the sender's payload, and that value hashes to the payment hash.
  - The stronger reading "no other preimage can match the hash" is a cryptographic
    assumption, not a model law. It is stated separately and proved conditional.
  - `LnLean.Proofs.Payment.KeysendProps` is imported because the `Keysend` record and
    its `Valid` predicate live there; no wave-E module is imported.

## Remaining gap / next step

No gap for the catalog claim. The only non-derivable strengthening is uniqueness of
the preimage among all byte strings, which is exactly C1 (`CollisionFree`/SHA-256
collision resistance) and remains an explicit hypothesis. `CollisionFree` as modelled
is stronger than computational collision resistance (it is exact injectivity on
preimages); this is the same idealisation used elsewhere in the scaffold.
