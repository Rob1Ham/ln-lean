## What is modelled

`FeasiblePath g L` is the explicit "valid multi-hop path" record:

| Field | Meaning |
|---|---|
| `path : List (ChannelEdge × Msat)` | one directed candidate edge plus the amount carried over it per hop |
| `nonempty` | BOLT 4 routes are non-empty |
| `conserved : BackwardConserves path` | at each forwarding hop, previous amount = this amount + this hop's fee |
| `connected : Connected path` | destination of each edge is the source of the next (the cross-channel link that `routeValid` does not check) |
| `mem_edges`, `enabled` | every used direction is an announced, enabled edge of the graph |
| `cltvPositive` | every used direction has `0 < cltv_expiry_delta` |
| `capacity` | forwarded amount fits `capacitySat * 1000` msat (BOLT 7 capacity) |
| `liquidity` | forwarded amount fits `L.availableMsat e`, the source node's explicit outbound-liquidity budget |

`LiquidityModel` carries `availableMsat : ChannelEdge → Nat` and the
explicit BOLT 7 bridge field
`withinCapacity : ∀ e, availableMsat e ≤ e.capacitySat * Msat.MSAT_PER_SAT`.
It is a structure, not an axiom.  `capacity_of_liquidity` proves that the
capacity precondition follows from the liquidity field plus this bridge.

The route itself is built with the existing `constructRoute` and is checked
by the existing `routeValid`; no route model was duplicated.

## Remaining obligations / modelling gaps

There are **no `sorry`s and no `PC3-...` obligation markers** in this
module.  The following are explicit modelling limits, not Lean obligations:

1. **LDK fee-index convention.** `LnLean.Routing.Route.Hop` stores the fee
   advertised by the edge *used to reach* the hop, so the first hop's fee is
   the sender's own channel policy and is not paid by the sender.  This is
   why the report states two identities: `Route.totalFee` is the sum of *all*
   hop fees, while the sender's outlay is the final amount plus
   `forwardFeeTotal` (all fees except the origin hop's).  Matching
   `rust-lightning`'s `RouteHop.fee_msat` exactly ("fee for use of the next
   channel") would require a `Hop` field distinguishing the incoming channel
   from the outgoing channel; that field does not exist in the current model.
2. **Liquidity is a bridge parameter.** `LiquidityModel.availableMsat` is
   supplied explicitly.  There is no `ChannelEdge → Channel` resolver in the
   repository (`MPPPart.channel` is a `ShortChannelId`, while `Channel` has a
   `ChannelId`), so the missing field is a real
   `resolveChannel : ChannelEdge → Option Channel` (or an equivalent
   `availableOutbound`-valued map on graph edges).  Once such a resolver
   exists, `FeasiblePath.liquidity` can be instantiated from
   `LnLean.Proofs.Payment.LiquidityProps.availableOutbound`.
3. **Onion payload, HMAC, MPP, route search, route blinding, and
   `min_final_cltv_expiry_delta`** are not modelled; this module only checks
   the amount/fee/CLTV arithmetic of an already selected path.
4. **Fee rounding** is the `Hop.ofEdge` over-estimate; no equality with
   LDK's integer arithmetic is claimed.
