## 3. Proof approach and helper lemmas

### `channelCapacityMsat_le_MSAT_MAX` (LN-FUND-002)

`channelCapacityMsat p` is `p.fundingSatoshis * MSAT_PER_SAT` in `Int`.
`FundingParams.WellFormed` gives
`p.fundingSatoshis ≤ MAX_MONEY = 21_000_000 * COIN` with
`COIN = 100_000_000` (`vendor/btc-lean-core/Bitcoin/Data/Basic.lean:116-122`,
`LnLean/Bitcoin/Funding.lean:99-105`), while
`Msat.MAX.val = 21_000_000 * SAT_PER_BTC * MSAT_PER_SAT`
(`LnLean/Basic/Core.lean:39-42`).  The proof:

1. reduces `hmax` to `p.fundingSatoshis ≤ 2100000000000000` by unfolding
   `Bitcoin.Data.MAX_MONEY`/`COIN`;
2. proves the closed numeral identity
   `(Msat.MAX.val : Int) = 2100000000000000 * MSAT_PER_SAT` with
   `unfold` + `decide`;
3. multiplies `hmax'` by the non-negative constant `MSAT_PER_SAT` with
   `Int.mul_le_mul_of_nonneg_right`;
4. rewrites the goal and applies that inequality.

No helper lemma was needed; the proof is inline.  A bare `omega` is not
enough because `Msat.MAX.val` reaches it as an opaque projection (and there
is no Mathlib `norm_num`), which is why the two numeral identities are closed
by `decide` first.  `decide` is core Lean, not `native_decide`.

### `witnessScript_parse_eq_none` (LN-FUND-001)

Not closed: the statement is false for the current model, as shown in §4.
The intended proof (for the well-formed case) is the byte trace
`0x52` → `const 2`, `0x21` → 33-byte push, `0x21` → 33-byte push, `0x52` →
`const 2`, then `decodeOp` on the final `0xae` returns `none` because
`ScriptInstr` has no `OP_CHECKMULTISIG` constructor
(`vendor/btc-lean-core/Bitcoin/Data/Script.lean:31-41`, `decodeOp`
`:53-71`).  That trace is exactly 71 bytes only when both keys are 33 bytes.

## 4. False statement: missing well-formedness hypothesis

**Claim under test.**  `witnessScript_parse_eq_none` quantifies over *all*
`FundingParams`, but `FundingParams.localFundingKey`/`remoteFundingKey` are
plain `PubKey`s whose `bytes : ByteArray` is unconstrained
(`LnLean/Basic/Core.lean:174-179`), and `pushData` only writes
`b.size.toUInt8` as the push-length byte (`LnLean/Bitcoin/Seam.lean:74-76`).
Nothing forces the two pushes to be 34 bytes each.

**Counterexample.**  Take

```lean
localFundingKey  = ⟨ByteArray.empty⟩
remoteFundingKey = ⟨0x04 0xaa 0xaa 0xaa 0xaa 0x4b ++ 73 × 0xaa⟩   -- 79 bytes
```

`orderedFundingKeys` keeps `(empty, 79-byte key)` (`listLexLE [] _ = true`),
so `pushData` yields the 84-byte witness script

```text
idx : 0    1    2    3    4..7      8    9..83
byte: 0x52 0x00 0x4f 0x04 aa aa aa aa 0x4b ... 0x52 0xae
```

`Script.parse ⟨...⟩ = parseWith b b.size 0 []` with `b.size = 84`, and the
fuel-based parser visits:

| step | index | byte | `decodeOp` result | next index | fuel left |
|---|---|---|---|---|---|
| 1 | 0 | `0x52` | `const 2` | 1 | 83 |
| 2 | 1 | `0x00` | `push []` (zero-length push) | 2 | 82 |
| 3 | 2 | `0x4f` | `op1negate` (this is the *length byte* of key 2) | 3 | 81 |
| 4 | 3 | `0x04` | `push` of 4 bytes (`0x04` is inside key 2) | 8 | 80 |
| 5 | 8 | `0x4b` | `push` of 75 bytes, indices 9..83 | **84 = size** | 79 |

`parseWith b 79 84 acc` then hits `b.size ≤ 84` and returns `some
acc.reverse`.  The last push swallows the trailing `0x52 0xae` as push data,
so the missing `OP_CHECKMULTISIG` opcode is never decoded.

**Reproduce (evaluated, not a kernel proof):**

```lean
import LnLean.Bitcoin.Funding
open LnLean LnLean.Bitcoin

def k2 : ByteArray :=
  ByteArray.mk ([0x04, 0xaa, 0xaa, 0xaa, 0xaa, 0x4b] ++
    List.replicate 73 (0xaa : UInt8)).toArray

def p : FundingParams :=
  { fundingSatoshis := 1000, pushMsat := ⟨0⟩
    localFundingKey := ⟨ByteArray.empty⟩, remoteFundingKey := ⟨k2⟩
    witnessScriptHash := ByteArray.empty
    temporaryChannelId := ⟨⟨ByteArray.empty⟩⟩ }

#eval p.witnessScript.bytes.size   -- 84
#eval p.witnessScript.bytes.toList -- [82, 0, 79, 4, 170, …, 75, 170, …, 82, 174]
#eval p.witnessScript.parse        -- some [const 2, push [], op1negate,
                                   --       push #[170,170,170,170],
                                   --       push #[…, 82, 174]]
```

The evaluated result is `some [...]`, hence `= none` is false.  (A
kernel-checked refutation would need `native_decide`, which the protocol
forbids; `decide`/`rfl` cannot reduce `ByteArray`'s extern primitives.)

**Missing model field / fix.**  The true and BOLT-3-relevant statement needs
the keys to be compressed 33-byte keys — i.e. the existing
`p.WellFormed` hypothesis (or the two conjuncts
`p.localFundingKey.bytes.size = 33` and
`p.remoteFundingKey.bytes.size = 33`).  For such `p` the script is the fixed
71-byte string `0x52 0x21 <key1> 0x21 <key2> 0x52 0xae`, both pushes are
consumed as data, and the final byte `0xae` is decoded as an opcode, for
which `decodeOp` has no branch (`ScriptInstr` has no `OP_CHECKMULTISIG`).
The statement was kept verbatim, with its `sorry` and obligation marker, so
the integration decision (add the hypothesis in a *new* corrected theorem,
or leave the obligation open) is left to the integrator.  This matters for
the interpreter bridge: `FundingSpendBridge` is still only an explicit
hypothesis and is not instantiated either way.
