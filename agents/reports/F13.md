# F13 — Invoice payment-secret binding

## Target
- Marker: `LN-WF-F13`
- Module: `LnLean.Proofs.ModelHardening.F13`
- Parent obligation: `LN-PM-SECRET` (the `payment_secret` half of LN-PM-003)

## Result
- Status: conditional (with a mechanized negative result for the unconditional claim)
- Build: RC 0 (`lake build LnLean.Proofs.ModelHardening.F13`, one expected `sorry` warning)
- New definitions:
  - `FinalPayload`: BOLT 4 final payload fields relevant to the binding
    (`paymentSecret`, `totalMsat`, `amtToForward`, `outgoingCltvValue`).
  - `FinalPayload.forInvoice`: constructor that copies the invoice's secret.
  - `FinalPayloadAcceptedFor fp i`: the missing final-node admission predicate,
    defined as `fp.paymentSecret = i.paymentSecret`.
  - `PaymentBridge i s fp`: full invoice/session/final-payload bridge
    (`s.paymentHash = i.paymentHash` plus `FinalPayloadAcceptedFor fp i`).
  - `UnconstrainedFinalAccept`: the shipped model's unconstrained acceptance
    relation (`True`), used only for the counterexample.
  - Concrete witness values `secretZero`, `secretOne`, `counterexampleInvoice`,
    `mismatchedPayload`.
- Main theorems:
  - `accepted_iff_secret_eq`: acceptance is exactly secret equality.
  - `accepted_secret_eq`: accepted payload carries the invoice's payment secret.
  - `accepted_secret_bytes_eq`: the corresponding byte strings are equal.
  - `accepted_secrets_eq`: two payloads accepted for one invoice agree on the
    secret (the LDK `check_merge` property, at the payload level).
  - `accepted_secret_size`: a structurally valid invoice forces every accepted
    payload's secret to be 32 bytes.
  - `accepted_of_invoice_secret_eq`: transport along equal invoice secrets.
  - `forInvoice_accepted`: a bridge-respecting payload can always be built.
  - `bridge_hash_and_secret` / `bridge_of_parts`: elimination and introduction
    for the full bridge.
  - `secretZero_ne_secretOne`: the two concrete 32-byte secrets differ.
  - `mismatchedPayload_not_accepted`: the mismatched payload is rejected by the
    bridge.
  - `unconstrained_accept_not_match`: a valid invoice and an unconstrained
    accepted payload can disagree on the secret.
  - `two_accepted_payloads_distinct_secrets`: one valid invoice has two
    unconstrained accepted payloads with different secrets.
  - `waveF_f13_unconditional_secret_match`: the faithful unconditional
    LN-PM-003 statement, false for the shipped model, with one `sorry` and the
    `-- OBLIGATION: LN-WF-F13` marker adjacent.
- Added hypotheses: matching is conditional on `FinalPayloadAcceptedFor`
  (equivalently on the BOLT 4 final-node secret check). No blanket assumption
  is made about arbitrary payloads or invoices. The existing `Invoice.Valid`
  hypotheses are explicit where the 32-byte result is used.
- Statement fidelity: LN-PM-003 is not weakened or restated as conditional
  only. Its unconditional form is retained verbatim with the marker and one
  `sorry`, and is refuted mechanically by
  `unconstrained_accept_not_match` / `two_accepted_payloads_distinct_secrets`.
  All positive matching results go through the explicit bridge predicate.

## Missing model field / next step

The shipped model has both halves in isolation but no link:

- `LnLean.Payment.Invoice.Invoice` has a mandatory `paymentSecret` field.
- `LnLean.Payment.HTLC.PaymentSession` has the invoice's `paymentHash` but no
  payment secret.
- `LnLean.Routing.Onion.OnionHop` (the terminal payload representation) has no
  `payment_secret` field at all, and no predicate relates it to `Invoice`.

Therefore the model cannot state, let alone prove, LN-PM-003 without adding a
final-payload record and a final-node admission predicate. This module supplies
both (`FinalPayload`, `FinalPayloadAcceptedFor`) and the full
`PaymentBridge`. The next model-hardening step is to adopt these definitions
(or equivalent fields) in the payment/onion model and make the final node
reject payloads that fail the bridge, so LN-PM-003 becomes an unconditional
model theorem. Until then, the unconditional statement remains false, as
mechanized here.

Note: the brief's import `LnLean.Payment.HTL` does not exist; the committed
module is `LnLean.Payment.HTLC`, which is what this file imports.
