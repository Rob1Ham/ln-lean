## Summary

This module formalises the two script paths of a BOLT 3 HTLC output:

1. a faithful two-branch witness-script template
   (`OP_IF <payment> OP_ELSE <timeout> OP_ENDIF`) together with its BIP 141
   P2WSH output commitment;
2. structural branch distinguishability via an explicit first-byte tag,
   requiring no cryptographic assumption;
3. injective parameter encodings: distinct payment hashes give distinct
   payment branches, and distinct four-byte CLTV expiries give distinct
   timeout branches;
4. conditional spendability, soundness, and authority disjointness through
   the explicit `HTLCSpendBridge` structure, whose four soundness/completeness
   fields are hypotheses (obligation `PC2-HTLC-001`), never axioms;
5. crypto consequences under `CollisionResistant sha256`: payment-preimage
   uniqueness and disjointness of payment branches for distinct preimages.

The L1 script interpreter stays abstract. `vendor/` was not touched.

## Newly discovered / recorded gaps

1. **Wave-A seam CLTV is one byte.** `LnLean.Bitcoin.htlcBranchScript` pushes
   `cltv.toUInt8`, so expiries `0` and `256` collide
   (`seamBranch_cltv_collision`). Its CLTV encoding is injective only below
   `256`, not on the BOLT 2 range. The faithful template therefore uses the
   fixed-width `pushScriptNum32` and is injective for all `c < 2^32`.
2. **Hash-lock opcode is a model marker.** The payment branch uses
   `OP_HASH160` as the model-level hash-lock marker; the concrete SHA-256
   opcode is outside the wave-A opcode subset. This is a template-level gap,
   not a proved equivalence.
3. **`pushData` has a one-byte length prefix.** It is faithful only for
   payloads below `256` bytes; all payloads in this module are 20, 32, or
   33 bytes, so the encodings used here are in range.
4. **No concrete CLTV/`OP_IF`/`OP_CHECKSIG` semantics.** These remain fields
   of `HTLCSpendBridge`; linking them to `Bitcoin.Data.Script` execution is
   the open `PC2-HTLC-001` work.
5. **Temporal disjointness is not unconditional.** `timeout_not_enabled_before_expiry`
   only says the timeout condition is false before expiry; the payment path
   can still be enabled then. The two branches are not disjoint in time; they
   are disjoint by authority (`branches_not_both_authorized_by_one_key`) and
   structurally (`paymentBranch_ne_timeoutBranch`).
