# F02 — Funding key parser safety

## Target
- Marker: `LN-WF-F02`
- Module: `LnLean.Proofs.ModelHardening.F02`

## Result
- Status: conditional
- Build: RC 0
- New definitions:
  - `FundingKeyParseSafe (k : PubKey) : Prop := k.bytes.size = 33`
  - `FundingKeysParseSafe (p : FundingParams) : Prop :=` both funding keys
    satisfy `FundingKeyParseSafe`
- Main theorems:
  - `fundingKeyParseSafe_iff_valid`: the invariant is exactly `PubKey.Valid`.
  - `fundingKeysParseSafe_of_wellFormed`: `p.WellFormed` implies the
    invariant, so every existing well-formed channel satisfies it.
  - `pushData_fundingKey_parseSafe`: a safe key is encoded as
    `0x21 <key>`; `pushData_fundingKey_prefix_not_opcode` proves `0x21` is a
    direct-push byte (`0 < 0x21 ≤ 0x4b`), not an opcode.
  - `decodeOp_pushData33`: generic parser lemma; a 33-byte push decodes to
    exactly `.push k` and consumes 34 bytes.
  - `fundingScript_key_pushes_decode`: for a parser-safe channel the first
    key decodes at offset 1 as `.push key1` (next index 35) and the second at
    offset 35 as `.push key2` (next index 69); the parser never interprets key
    bytes as opcodes.
  - `waveF_f02_witnessScript_parse_eq_none_of_parseSafe`: the corrected
    parse theorem. Under `FundingKeysParseSafe p`, the BOLT 3 witness script
    parses through `OP_2 <key1> <key2> OP_2` and stops at the trailing
    `OP_CHECKMULTISIG`, hence `p.witnessScript.parse = none` in the wave-A
    parser (no `OP_CHECKMULTISIG` constructor).
  - `waveF_f02_cex79`: two 79-byte keys (`0x4f` is `OP_1NEGATE`) make
    `witnessScript.parse ≠ none`.
  - `waveF_f02_cex81`: two 81-byte keys (`0x51` is `OP_1`) also make
    `witnessScript.parse ≠ none`.
- Added hypotheses: `FundingKeysParseSafe p`, i.e. both funding keys are
  exactly 33 bytes. This is *not* implied by the bare `FundingParams`
  structure; it is implied by `FundingParams.WellFormed` and is exactly the
  hypothesis missing from the scaffold's unconditional
  `FundingProps.witnessScript_parse_eq_none`.
- Statement fidelity: the unconditional 71-byte parse claim is false for the
  model as written, so it is not asserted here. The faithful conditional form
  is proved outright (no `sorry` in this module), and the two unsafe sizes
  are mechanized as counterexamples. No claim was silently weakened.

## Missing model field / next step

`FundingParams` does not carry a key-length well-formedness field, and
`LnLean.Bitcoin.pushData` writes `b.size.toUInt8` without a range check or
`OP_PUSHDATA1/2` handling. Sizes 79 and 81 therefore emit length bytes that
`Bitcoin.Data.decodeOp` reads as `OP_1NEGATE` and `OP_1`; the following key
body is then decoded as opcodes and can swallow the trailing
`OP_2 OP_CHECKMULTISIG`, so the whole script is accepted. Two model fixes are
needed:

1. Make the key-length invariant part of the parser-facing funding API (or of
   `FundingParams.WellFormed` if a single predicate is preferred), and make
   `pushData` reject/encode correctly for lengths outside `1..75`.
2. Add an `OP_CHECKMULTISIG` constructor (or an explicit unsupported-opcode
   result) to `Bitcoin.Data.ScriptInstr`; the current parser returns `none`
   for every correctly built funding script, which prevents a positive
   full-script parse theorem.
