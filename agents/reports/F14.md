# F14 — MPP running-total invariant

## Target
- Marker: `LN-WF-F14`
- Module: `LnLean.Proofs.ModelHardening.F14`
- Parent obligation: `LN-PM-MPP` (traceability row `LN-PM-005`)

## Result
- Status: counterexample
- Build: RC 0 (`lake build LnLean.Proofs.ModelHardening.F14`, one intentional
  `sorry` warning at the marker)
- New definitions:
  - `RunningTotalBound (target : Msat) (collected : List MPPPart)`:
    `sumParts collected ≤ target.val`.
  - `PartFits (target : Msat) (collected : List MPPPart) (p : MPPPart)`:
    `p.amount.val ≤ target.val - sumParts collected` (the remaining-budget
    admission guard).
  - Counterexample fixtures `demoPart`, `demoPlan`, `overTotalPlan`.
- Main theorems:
  - `runningTotalBound_nil`: the empty collection satisfies the invariant.
  - `runningTotalBound_add`: **preservation under the guard** —
    `RunningTotalBound target collected` and `PartFits target collected p`
    imply `RunningTotalBound target (p :: collected)`.
  - `runningTotalBound_add_iff`: for a collection already inside the bound,
    preservation is *equivalent* to `PartFits`; no weaker per-part check can
    replace the guard.
  - `partFits_iff_add_le`: under the invariant the guard is exactly
    `sumParts collected + p.amount.val ≤ target.val`.
  - `runningTotalBound_append`: batch admission when the batch sum fits the
    remaining budget.
  - `runningTotalBound_mono`: the bound is monotone in the advertised total.
  - `runningTotalBound_of_mppComplete` and
    `mppComplete_of_runningTotalBound_of_ge`: completeness/terminal-state
    bridge (the second is the exact-sum form of BOLT 4's
    `collected ≥ total_msat`).
  - `not_partFits_of_sum_eq_target`: once the collected total equals the
    target, no positive part can pass the guard.
  - `sumParts_cons_lt_of_pos`: a positive part strictly increases the
    running total.
  - `not_runningTotalBound_cons_of_over`: over-total is absorbing.
  - `waveF_f14_running_total_bound`: the faithful unconditional statement,
    with one `sorry` and the unique `-- OBLIGATION: LN-WF-F14` marker.
  - `overTotal_counterexample`: mechanized refutation of the unconditional
    statement.
  - `overTotal_each_part_within_target`: both 60 msat parts individually pass
    `amount ≤ total_msat = 100`.
  - `overTotal_second_part_guard_fails`: the second 60 msat part fails the
    remaining-budget guard (`60 ≤ 100 - 60` is false).
  - `overTotal_not_runningTotalBound` and `overTotal_not_complete`: the
    over-total plan violates `RunningTotalBound` and is not `mppComplete`.
- Added hypotheses: the preservation theorem assumes the invariant on the
  current collection plus `PartFits` for the new part.  The unconditional
  theorem assumes only the invariant; that is precisely why it is false.
- Statement fidelity: the obligation text "each additional part keeps the
  running total at or below `total_msat`" is formalized as
  `∀ plan collected p, RunningTotalBound plan.target collected →
     RunningTotalBound plan.target (p :: collected)`.
  This exact statement is kept as `waveF_f14_running_total_bound` with the
  marker.  It is false: parts 60 and 60 under a 100 msat target preserve the
  bound after the first part but reach 120 after the second.  The guarded
  `runningTotalBound_add` is the strongest true preservation form, and
  `runningTotalBound_add_iff` shows the guard cannot be weakened.  The model's
  `mppComplete` is exact-sum, so an over-total collection is not complete.

## Missing model field / next step

The model has `MPPPlan.target` (BOLT 4 `total_msat`) but no collection
transition or admission function that enforces the remaining-budget guard.
`sumParts` is a pure list sum, so the guard must be supplied by the caller;
`PartFits` is the reusable predicate for that purpose.  A next step is to add
an `addPartWithinBudget`-style collector to `LnLean.Payment.MPP` whose result
carries `RunningTotalBound`, and to connect the BOLT 4 lower-bound completion
(`collected ≥ total_msat`, including overpay) to the BOLT 11 invoice amount
for `LN-PAY-MPP-OVERPAY`.  The current model also still lacks an `htlc_id`, so
same-channel/same-CLTV parts remain distinguishable only by full record
equality.
