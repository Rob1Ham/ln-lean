### The single obligation

`LN-KS-001` — “A keysend whose every settlement outcome is a failure never
reveals its preimage.” Statement:

```lean
theorem all_failed_outcomes_never_reveal (k : Keysend) (os : List PaymentState)
    (hk : k.session.state = .pending) (hall : ∀ o ∈ os, o = .failed) :
    (k.applyOutcomes os).revealedPreimage = none
```

This is true in the model: the first `.failed` makes the session terminal, and
`settle_terminal_state` (already proved) shows every later settlement is a
no-op, so the state can never become `.succeeded`. The next smallest step is
to prove it by induction on `os`: in the cons case use `settle_terminal_state`
with `≠ .pending` (derived from the just-established `.failed` state) to show
the tail is absorbed, then invoke `pending_not_revealed`/the induction
hypothesis. Nothing in the statement depends on cryptography.

## 4. What remains open / honest gaps

1. **LN-KS-001** above: the trace-level non-revelation theorem is stated and
   `sorry`ed. Everything it needs (`settle_terminal_state`,
   `pending_not_revealed`, `applyOutcomes_*`) is already proved in the file.
2. **`PaymentSession` has no origin field.** The wave-A session type stores
   only hash/amount/parts/state. `paymentSession_forgets_origin` proves this
   is a genuine information loss, so the non-confusion law is stated on
   `TaggedSession`, which lives in this proof file. If the integrator wants
   the property in the model, `Payment/HTLC.lean` needs a `kind` field on
   `PaymentSession`; that file is not mine to edit. Until then read
   “keysend and invoice payments cannot be confused” as “*given the origin
   tag*, they cannot be confused”.
3. **`CollisionFree` is an idealization of C1.** Ordinary collision
   resistance does not imply injectivity of a total function; theorems 31–32
   are therefore conditional on an explicitly named hypothesis, not on an
   axiom. Computational preimage resistance is not formalized (it is not a
   `Prop` about a total function). No claim here should be read as
   “the preimage cannot be computed from the hash”.
4. **Onion/TLV transport is not modelled.** `msgs.rs:3643` (TLV
   `5482373484`) and the onion-payload path are cited but not built. The
   module starts from a recipient that already holds the preimage; the wire
   check is the `Keysend.Valid` hypothesis.
5. **Recipient policy / acceptance is out of scope.** The model says what
   holds if a keysend is accepted (`Valid`) and settled; it does not say a
   node must accept spontaneous payments. The optional BOLT 4
   `payment_secret` interaction (`payment_data` vs spontaneous path) is only
   cited, not proved.
6. **Keysend MPP.** `create_single_part` makes keysend single-part in this
   model; splitting a keysend is not represented.
