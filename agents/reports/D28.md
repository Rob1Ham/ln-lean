# D28 — A BOLT 11 invoice signature is valid for the payee node key.

## Target

- Parent/catalog: `LN-PM-002`
- Module: `LnLean.Proofs.WaveD.D28`
- File: `LnLean/Proofs/WaveD/D28.lean`

## Result

- Status: conditional
- Build: RC 0
  (`flock -w 900 /tmp/ln-build.lock lake build LnLean.Proofs.WaveD.D28`,
  Lean `v4.35.0`, 11 jobs, 690 ms)
- Theorems/definitions:
  - `signatureValidForPayee` — named form of the second component of
    `Invoice.verify`: `sigCheck i.payee (digest i) i.signature = true`.
  - `waveD_d28_verify_iff` — `Invoice.verify` is exactly `i.Valid ∧
    signatureValidForPayee` (proved, `Iff.rfl`).
  - `waveD_d28_signature_valid_for_payee` — **main target**: every verified
    invoice's signature is valid for its own payee key (proved, no crypto
    premise).
  - `waveD_d28_accepting_check_is_payee` — the accepting check is invoked with
    `i.payee` as key and `digest i` as message (proved).
  - `waveD_d28_verified_payee_size` / `waveD_d28_verified_signature_size` — a
    verified invoice's payee key is 33 bytes and its signature is 65 bytes
    (proved from `Invoice.Valid`).
  - `SignatureKeyBinding` — premise: a message/signature pair is accepted by at
    most one `PubKey` (algebraic shadow of recoverable-ECDSA key recovery).
  - `waveD_d28_accepting_key_eq_payee` — under `SignatureKeyBinding`, any key
    that accepts the verified invoice's signature equals `i.payee` (proved).
  - `waveD_d28_signing_key_unique` — under `SignatureKeyBinding`, two verified
    invoices with the same digest and the same signature have the same payee
    (proved).
  - `waveD_d28_recovered_key_unique` — uniqueness of the "recovered" key
    (proved).
  - `waveD_d28_signature_binds_digest` — under `Crypto.Model.EufCma sigCheck`,
    one payee key's signature determines the signable digest (proved).
  - `waveD_d28_signature_binds_invoice` — under `EufCma` plus an injective
    digest function, a payee key plus its signature determines the whole
    invoice (proved).
  - `waveD_d28_cex_payees_distinct`, `waveD_d28_cex_valid_a/b`,
    `waveD_d28_cex_verify_both`, `waveD_d28_cex_same_message_and_signature` —
    a mechanically checked pair of valid invoices with distinct payees, the
    same digest and the same signature, both accepted by a key-ignoring
    checker.
  - `waveD_d28_unconditional_binding_false` — **negative result**: the
    unconditional form "same digest + same signature + joint verification
    implies equal payees" is false for the model (proved).
  - `waveD_d28_key_binding_not_free` — the key-ignoring checker is not
    `SignatureKeyBinding`, so the conditional theorems are not vacuous
    (proved).
- Added hypotheses:
  - `SignatureKeyBinding sigCheck` for the uniqueness/recovery theorems. This
    is the missing model/crypto field: `Invoice.verify` takes `sigCheck` as an
    arbitrary `PubKey → ByteArray → InvoiceSignature → Bool`, so nothing in the
    model forces a signature to determine its verification key.
  - `LnLean.Crypto.EufCma sigCheck` and `Function.Injective digest` for the
    two "signature binds the data part/invoice" theorems. The scaffold's
    `Crypto.Model.EufCma` fixes a key and binds the message; it does not imply
    key binding.
  - No other hypotheses. All other theorems are unconditional.
- Statement fidelity:
  - The catalog claim is model-level: LDK `Bolt11Invoice::check_signature`
    (`lightning-invoice/src/lib.rs:1025`) verifies the compact signature over
    the stored digest under `payee_pub_key()`. The model's `Invoice.verify`
    encodes exactly that branch (LDK's `Some(pk)` case), so
    `waveD_d28_signature_valid_for_payee` is the faithful unconditional
    reading and is proved with no `sorry`.
  - The stronger reading — the payee key is *the* signing key and is unique —
    is not derivable from the model and is stated conditionally. The
    counterexample shows the gap is real, not a proof failure.
  - No claim was weakened silently; every extra premise is named above and in
    the module docstring.

## Remaining gap / next step

- The BOLT 11 signable-digest construction (HRP + data part, bech32 encoding)
  is not modelled; `digest : Invoice → ByteArray` remains a parameter. Closing
  it is `LN-PAY-INVOICE-ENCODING`.
- Recoverable ECDSA / secp256k1 public-key recovery is not modelled. A concrete
  instantiation should provide `sigCheck` from `LnLean.Crypto.Model` together
  with a proved `SignatureKeyBinding` (or a `recover` function plus
  soundness/completeness), at which point `waveD_d28_accepting_key_eq_payee`
  and `waveD_d28_signing_key_unique` become unconditional for that instance.
- The `n`-field-absent case (payee key recovered from the signature) is out of
  scope: `Invoice` always carries an explicit `payee`.
