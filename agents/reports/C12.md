## 3. Proof approach and helper lemmas

The two obligations reduce to the same list/record fact: `receive` either
leaves `channels` untouched (handshake branch) or applies
`updateChannel s cid (fun _ => c.advanceReceived m)` (channel branch), and
`advanceReceived` preserves the channel identifier.

Private helpers added (same file, all used):

1. `List.find?_map_of_find?_eq_some` — list induction: mapping by a function
   that fixes every element failing the predicate, and maps the found element
   to a value still satisfying the predicate, preserves `find?`.
2. `findChannel_updateChannel_of_channelId` — specializes the list lemma to
   `findChannel`/`updateChannel`, using only the fact that the update preserves
   the found channel's id.
3. `advanceReceived_channelId` — `advanceReceived` never changes
   `ChannelRecord.channelId` (case split on `MsgKind`, then on the
   `revoke_and_ack` guard).
4. `receive_of_no_event` — the exact result of the non-handshake channel branch
   of `receive`, derived from the accepted-receive hypothesis.
5. `receive_of_event` — the exact result of the handshake branch of `receive`,
   again derived from the accepted-receive hypothesis. The `transport = down`
   subcases are discharged because the hypothesis forces an `Option.some`.

For LN-REEST-002 the proof splits on `receiveEvent? m`: in the `none` branch
the monotonicity comes from the already-proved
`advanceReceived_counters_monotone`; in the `some e` branch the peer state only
changes its handshake field, so the channel and both counters are unchanged.

No statement was weakened and no statement was found false for the current
model.
