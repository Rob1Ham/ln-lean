## 2. Claim and structure

The file proves conservation for the two close paths on one L1 funding
value, using the existing `Balance`, `Commitment`, `buildCommitment`,
`commitmentFee`, and `feeForWeight` definitions.

### Cooperative close

`CooperativeClose` is the value core of a `closing_signed` transaction:
two closing outputs and one negotiated closing fee.

`cooperativeClose b fee funder` pays `b.localSat` and `b.remoteSat`
directly, except that the funder subtracts `fee` from its own output.  The
only non-truncation hypothesis is

```lean
fee ≤ funderBalance b funder
```

where `funderBalance b .local = b.localSat` and
`funderBalance b .remote = b.remoteSat`.  Under it,
`cooperativeClose_distributes` states exactly one of the two cases:

```lean
(funder = .local  ∧ localOut + fee = b.localSat ∧ remoteOut = b.remoteSat) ∨
(funder = .remote ∧ localOut = b.localSat ∧ remoteOut + fee = b.remoteSat)
```

`cooperativeClose_outputs_add_fee` then gives
`localOut + remoteOut + closingFee = b.localSat + b.remoteSat`, and
`cooperativeClose_conserved` packages this as `conserved`.

`CooperativeClose.ofFinalCommitment` bridges a final zero-HTLC,
non-anchor `Commitment` to the cooperative-close record:
`ofFinalCommitment_totalOutputValue` proves the output totals agree, and
`ofFinalCommitment_conserved` transfers conservation.

### Unilateral close

The current commitment is the existing `buildCommitment`, which subtracts
the fee, the holder output, the untrimmed HTLC values, and the anchor total
from the funding value.  The exact non-truncation bound is

```lean
fee + toLocal + htlcOutputsValue htlcs + commitmentAnchorTotal anchors ≤ funding
```

Under it, `unilateralClose_conserved` proves

```lean
CommitmentConserved (buildCommitment holder number funding fee toLocal
  htlcs contestDelay anchors)
```

i.e. emitted outputs plus `feeSat` equal `fundingValueSat`.  This covers
arbitrary untrimmed HTLCs, both anchor settings, and both holders.

The CSV contest delay is metadata only.  `contestDelay_totalOutputValue`
proves that changing `contestDelay` leaves `totalOutputValue` unchanged;
`contestDelay_conserved_iff` shows conservation is unaffected;
`contestDelay_no_value_creation` shows the delayed output still cannot
exceed the funding value; and `unilateralClose_contestDelay_conserved`
re-establishes conservation after an arbitrary delay change.

### Agreement of the two paths

`ClosePaths` packages a cooperative close and a unilateral commitment with
a proof field `sameFunding : cooperative.fundingValueSat =
unilateral.fundingValueSat`.  Then:

* `closePaths_totals_agree`: if both conserve, their “outputs plus fee”
  totals are the same number, namely the shared funding value;
* `closePaths_output_totals_agree_of_fee_eq`: if the two fees also agree,
  the output totals themselves agree;
* `cooperative_unilateral_agree` and
  `cooperative_unilateral_output_totals_eq_of_fee_eq` instantiate both
  statements from one `Balance` and the satoshi funding value
  `b.localSat + b.remoteSat`.

### Fee bounds

* `cooperativeClose_fee_le_funding`: agreed closing fee ≤ funding value,
  via `funderBalance_le_total`;
* `cooperativeClose_closingFee_le_fundingValue`: the same bound on the
  close record;
* `unilateralClose_fee_le_funding`: commitment fee ≤ funding value under
  the unilateral non-truncation bound;
* `unilateralClose_requiredFee_le_funding`: any feerate-derived
  `commitmentFee` covered by the recorded fee is also ≤ funding.

  anchor outputs from the funder.  That gap is already recorded in
  `CommitmentTxProps.commitmentPair_conservation_anchors_gap`; this module
  therefore uses `buildCommitment` for the general unilateral path, which
  does subtract `commitmentAnchorTotal anchors`.
* As with the rest of the value accounting, the `Balance` to satoshi
  conversion is the existing floor conversion; sub-satoshi remainders are
  outside the commitment transaction equation.

  theorem module and this report.
