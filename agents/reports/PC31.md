## Claims proved

1. The retransmission-eligible message set is exactly the retained messages
   of the five `retransmittable` kinds, is enumerated by a list of length
   `≤ 5`, and is a subset of the explicit five-slot recent-message buffer.
2. Any reconnect inbox (including `channel_reestablish`) leaves every
   retained slot and therefore the retransmission window unchanged, so the
   post-reconnect window is still `≤ 5`, and a retained `channel_ready`
   remains eligible.
3. Outbound retention leaves both reestablish counters equal; inbound
   receipts never lower either. Hence `ReconnectTrace` (send/receive
   interleavings across a reconnect) is monotone in both counters.
4. An accepted `channel_reestablish` yields at most two retransmission
   candidates (one `commitment_signed`, one `revoke_and_ack`), both drawn
   from the five-slot buffer, with the commitment number in BOLT 2's
   last-sent / last-sent+1 window.

Newly discovered gap (modelling, not a proof gap): the five-slot capacity is
a property of the wave-A `ChannelRecord` shape, not of BOLT 2 — a real node
may retain per-update data. The module states this explicitly in
`retransmitBufferCapacity` and `bufferCapacity_eq_slots` rather than
pretending the bound is protocol-derived. A second model caveat inherited
from `ChannelReestablishProps` is that duplicate `commitment_signed`
messages are not detected (`advanceReceived` advances on every receipt), so
the window proves *which retained messages are eligible*, not that a
retransmitted message is fresh.
