## 4. What remains open, and the next smallest step

1. **Peer-level receipt lemma (LN-REEST-001/002).**  Next step: prove, by
   induction on `s.channels`,
   `findChannel (updateChannel s cid f) cid = some (f c)` from
   `findChannel s cid = some c`, `(f x).channelId = x.channelId`, and
   `List.find?_cons`.  Then `advanceReceived` gives the unchanged counters.
2. **Duplicate detection is not modelled.**  `Msg.commitmentSigned` has no
   commitment number, so `advanceReceived` advances on every replay
   (`duplicate_commitmentSigned_advances_twice`, checked).  The file proves
   the idempotent refinement `advanceReceivedNumbered` but the wave-A
   `PeerState.receive` does not use it.  Next step (outside this file):
   extend `CommitmentSigned` with its commitment number in `Protocol/Messages`,
   then switch `advanceReceived` to the numbered form.
3. **`Step.revokeAndAck` has no guard.**  `reachable_counters_inconsistent`
   is a checked counterexample: two `revoke_and_ack` receipts take a normal
   channel to `localCommitmentNumber = 2`, `remoteCommitmentNumber = 0`,
   which violates the reestablish consistency predicate under `countersOf`.
   Next step: add `localCommitmentNumber < remoteCommitmentNumber + 1` (or
   `remote < local`) as a precondition to `Step.revokeAndAck` in
   `Channel/State.lean`; this file correctly does not assume it.
4. **Counter origin mismatch.**  BOLT 2 says `next_commitment_number` starts
   at 1 (`:3607`), while `ReestablishFields.initial` is 0.  Theorems are
   stated over both conventions; `ReestablishAccepted` only requires
   `0 < nextCommitmentNumber`, so the initial value is rejected as BOLT
   requires for a non-established channel.
5. **`channel_ready` "both sides" test.**  `PeerState.receive` does not store
   the inbound `channel_reestablish` counters, so the BOLT conjunction is an
   explicit `ReconnectView` parameter.  Next step: add a
   `lastReceivedReestablish : Option ReestablishFields` to `ChannelRecord`
   and derive the view from the record.
6. **Data-loss-protect exactness.**  Only the forward direction
   (`next_revocation_number = 0 → all zeroes`) is BOLT law.  The converse
   needs the received secret to be non-zero, which is a cryptographic fact
   (C1/C6), stated conditionally in `dataLossSecretExact_of_lastSecret`.
7. **Rejection is not a transition.**  `ReestablishRejected` is a `Prop`;
   neither `PeerState` nor `Channel` has an error/close state, so "send
   `error` and fail the channel" is not modelled.
8. **Out of scope:** `shutdown`/`closing_signed` retransmission, `next_funding`,
   `my_current_funding_locked`, `announcement_signatures`, splicing, and wire
   byte encoding.
