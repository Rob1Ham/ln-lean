## Why the remaining obligations are blocked

1. **`LN-GOSSIP-001`** — `ChannelUpdate.signingKey` is an independent field
   and `SigVerifier` is an arbitrary function.  `acceptChannelUpdate` checks
   only `u.signatureValid verify` and the timestamp; it never looks at
   `s.announcements`.  Counterexample: `acceptAll`, `gapState = ⟨[], [], []⟩`,
   `gapUpdate` with `timestamp = 1` and an unannounced empty key.  Acceptance
   adds the update but there is no announcement to supply the key.
2. **`LN-GOSSIP-002`** — `ChannelAnnellation.capacitySat : Nat` has no
   positivity invariant, and `bindChannel` copies it without a check.
   Counterexample: `zeroAnn` with `capacitySat = 0` under `acceptAll` binds to
   `zeroBinding` with `capacitySat = 0`.
3. **`LN-GOSSIP-003`** — `GossipSignature.Valid` is `bytes.size = 64`, but
   `SigVerifier` has no length contract.  Counterexample: `acceptAll` accepts
   `gapUpdate` whose signature is `emptySig` (`bytes.size = 0`).

## Next smallest steps

1. `LN-GOSSIP-001`: make the admission path require the announced key, e.g.
   add `updateKeyAnnounced s u` to the guard in `acceptChannelUpdate` (or
   remove `signingKey` from `ChannelUpdate` and look it up in the store).
   Then the original follows from
   `accepted_update_signing_key_announced_of_key_admission`.
2. `LN-GOSSIP-002`: add `hcap : 0 < a.capacitySat` to `bindChannel` (or use
   a positive-capacity subtype).  Then
   `bindChannel_capacity_positive_of_announced` composes directly.
3. `LN-GOSSIP-003`: add a `signature.Valid` check to the admission path (or
   carry the verifier length contract `hlen`).  Then
   `accepted_update_signature_length_of_verifier_length` composes directly.
