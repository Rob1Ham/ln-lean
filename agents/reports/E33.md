# E33 — Safety holds under an asynchronous adversarial schedule (without a fairness hypothesis).

## Target

- Parent/catalog: `LN-SEC-003`
- Module: `LnLean.Proofs.WaveE.E33`
- File: `LnLean/Proofs/WaveE/E33.lean`

## Result

- Status: proved
- Build: RC 0 with
  `export PATH=/dev/shm/btc/elan/toolchains/leanprover--lean4---v4.35.0/bin:$PATH && cd /home/ubuntu/ln-lean-wavee && flock -w 900 /tmp/ln-build.lock lake build LnLean.Proofs.WaveE.E33`
- Theorems/definitions:
  - `waveE_e33_run_invariant` — if `Safe` holds initially and is preserved by
    every `step` under every adversary and step index, then `Safe` holds at
    every finite horizon.
  - `waveE_e33_secure_of_invariant` — the same induction gives `Secure g`
    whenever `bad` implies `¬ Safe`.
  - `ChannelMsg`, `AsyncChannelState`, `delivered`, `asyncStep`,
    `asyncChannelGame` — an asynchronous channel network: a `Ledger` plus a
    queue of BOLT 2-style messages (`update_add_htlc`, fulfil, fail, fee as
    `LedgerOp`s). A message is applied only when
    `Adversary.schedule.delivery n dst = true` and `(src, dst)` is not
    partitioned; otherwise the step stutters (message delayed beyond the
    horizon). An unavailable ledger operation also stutters via
    `Option.getD`.
  - `waveE_e33_getD_step_conserves`,
    `waveE_e33_asyncStep_conserves` — every single step, delivered or
    delayed, available or rejected, preserves
    `local + remote + in-flight + fee = funding`
    (reusing `Ledger.step_conserves` from `LnLean.Security.Invariants`).
  - `waveE_e33_safety_async` — **headline**: for every initial queue order,
    every conserving initial ledger, and every `Adversary`,
    `Secure (asyncChannelGame init a)`.
  - `waveE_e33_run_conserves` — the unfolding of the headline at every
    horizon.
  - `waveE_e33_applyAll_conserves` — any finite list of ledger operations,
    applied in any order with availability checks, preserves conservation
    (order irrelevance, so message reordering cannot break safety).
  - `lossySchedule`/`lossyAdversary`, `chaoticSchedule`/`chaoticAdversary`,
    `fullyPartitionedSchedule`/`fullyPartitionedAdversary` — three concrete
    adversarial schedules (drop everything, deliver everything in queue
    order, partition every pair).
  - `waveE_e33_lossy_step_stutters`, `waveE_e33_lossy_run_eq`,
    `waveE_e33_partitioned_step_stutters` — the lossy and fully partitioned
    runs are constant.
  - `waveE_e33_chaotic_step_queue`, `waveE_e33_chaotic_run_queue`,
    `waveE_e33_chaotic_delivers_all` — under the delivering schedule exactly
    one queued message is consumed per step, so the queue empties after
    `queue.length` steps (non-vacuity).
  - `waveE_e33_genesisLedger_conserves`, `waveE_e33_chaotic_inflight_after_one`
    — concrete witness: a 100 msat `update_add_htlc` is actually delivered,
    moving value from `localBalance` to `inFlight` while the total stays
    `1000`.
  - `waveE_e33_lossy_liveness_fails`,
    `waveE_e33_partitioned_liveness_fails` — the same runs that satisfy
    safety never empty their queue, so no progress/liveness property holds.
    This is the mechanized separation: fairness is needed for liveness, not
    for safety.
  - `waveE_e33_no_fairness_needed` — the headline restated with the four
    schedule fields (`delivery`, `partition`, `maxDelay`, `reorders`,
    `dropsMessages`) universally quantified, making the absence of any
    fairness, bounded-delay, or eventual-delivery hypothesis explicit.
- Added hypotheses: none beyond the standard initial-condition hypothesis
  `init.ledger.Conserves` and the arbitrary `Adversary`/initial queue. There
  is no fairness, partial-synchrony, GST, bounded-delay, or "eventually
  delivered" hypothesis. `init.ledger.Conserves` is required because the
  theorem is an invariant-induction result, not a statement that an arbitrary
  ledger is consistent.
- Statement fidelity: the catalog target is `Secure g`, i.e.
  `∀ n, ¬ g.bad (g.run n)`. The concrete instance takes
  `bad s := ¬ s.ledger.Conserves`, one of the ten core safety invariants
  (INV-01, value conservation). Delivery, delay, loss, partition and queue
  order are controlled by the adversary; the only assumptions that make the
  result true are model assumptions: (i) `Ledger.step` rejects unavailable
  operations instead of moving value, (ii) `SecurityGame.step` is total and a
  non-delivery is a stutter, and (iii) conservation is an arithmetic state
  invariant rather than a payment-success event. `SecurityGame.honest` is
  `[]` in this instance deliberately: the protected event is ledger
  conservation, and the module makes no claim about a protected node set.
  No `sorry`, `axiom`, `admit`, `native_decide`, `unsafe`,
  `@[implemented_by]`, or Mathlib. Only
  `LnLean.Security.Invariants` and `LnLean.Security.Model` were imported
  (the Bitcoin/Channel/Routing law bundles are not used by this target).

## Remaining gap / next step

`SecurityGame.step` remains an unconstrained field, so this is a proof for one
faithful asynchronous ledger instance plus a generic safety-induction
principle, not a refinement of the real `channelmanager.rs` state machine.
The next step is to instantiate `asyncStep` with the concrete channel state
machine (commitment numbers, HTLC set, revocation secrets) and to replace the
ledger-only `bad` predicate with the payment-event predicate of
`LN-SEC-006`/`LN-SEC-002`. The model's `NetworkSchedule` has no reordering
chooser, so runtime reordering is represented by an arbitrary initial queue
order; `waveE_e33_applyAll_conserves` and the `∀ queue` quantification cover
every order for safety, but a future model could add an explicit delivery
selector for a finer trace semantics.

Note on naming: `LnLean.Proofs.Security.ThreatModelProps` §10 uses the label
`LN-SEC-003` for the `HonestDisjoint` gap. The 48-row catalog row `LN-SEC-003`
is the asynchronous-safety claim targeted here; this module follows the
catalog row specified in the brief.
