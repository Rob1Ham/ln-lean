## 1. What this adds

`scripts/waveh/verify-vendor-artifact.sh` is a read-only, network-free check for
a **candidate snapshot directory** before it is published, installed, or
archived. It answers three publication questions that the existing gates do not
answer together:

| Question | Existing gate | This verifier |
|---|---|---|
| Do all 119 tracked source files match `vendor/VENDOR-SHA256`? | `scripts/verify-vendor.sh` (yes) | yes, independently reimplemented |
| Is the manifest itself well-formed and canonical? | `verify-vendor.sh` only `diff`s it | yes: count, `sha256sum` grammar, path safety, duplicates, order |
| Does the snapshot contain a symlink, specifically the OPS-04 absolute link? | no — `verify-vendor.sh` hashes `find -type f`, so symlinks are invisible | yes: absolute and relative symlinks are both reported and rejected |

The OPS-04 defect is exactly this entry in the pinned snapshot:

```
vendor/btc-lean-core/btc-lean-core -> /home/ubuntu/ln-lean/vendor/btc-lean-core
```

It is not in the 119-file manifest, does not affect the digest, and cannot be
seen by the existing checksum gate. It *is* rejected by
`scripts/fetch-vendor.sh` when an archive is unpacked (`unsupported archive
member`), but there was no standalone check for an already-extracted candidate
directory. This script is that check.

It does not provision, repair, delete, or publish anything. It only reads.

## 2. Inputs and defaults

```
scripts/waveh/verify-vendor-artifact.sh [--artifact DIR] [--manifest FILE] [--strict-root]
```

| Option | Default | Meaning |
|---|---|---|
| `--artifact DIR` | `vendor/btc-lean-core` | Candidate snapshot directory. Relative paths resolve from the repository root. |
| `--manifest FILE` | `vendor/VENDOR-SHA256` | Per-file pin. Relative paths resolve from the repository root. |
| `--strict-root` | off | Treat a symlinked artifact *path* as a failure. Without it, a symlinked root is reported as a note and the resolved tree is scanned (the shared worktree uses such a link for `vendor/btc-lean-core`). |
| `-h`, `--help` | — | Usage text. |

The script finds the repository root from its own location, so it can be invoked
from any working directory.

## 3. Exact checks

1. **Artifact shape**
   - `ARTIFACT` must exist; a missing path exits `3` with the OPS-01
     provisioning hint.
   - It must be a directory, contain `lakefile.lean`, and contain
     `Bitcoin.lean`; otherwise exit `1`.
   - If the path itself is a symlink, its target is classified as absolute or
     relative. It is a note by default and a failure under `--strict-root`.

2. **Manifest canon (`EXPECTED_FILES=119`)**
   - exactly 119 newline-terminated entries;
   - every line is the `sha256sum` form `SHA256  ./relative/path`;
   - digest is 64 lowercase hex characters;
   - path starts with `./` and a non-`/` character, has no `//`, no backslash,
     no `..` component, and is not under `./.lake` or `./.git`;
   - no duplicate paths;
   - entries are in `LC_ALL=C` path order (the canonical order produced by
     `find | sort -z | sha256sum`).

3. **119-file digest**
   - from inside the artifact:
     `find . \( -path ./.lake -o -path ./.git \) -prune -o -type f -print0`
     → `LC_ALL=C sort -z` → `xargs -0 -r sha256sum`;
   - compared path-by-path against the manifest, with separate
     `missing` / `extra` / `changed` counts and up to five example paths per
     category. The `.lake`/`.git` pruning deliberately matches
     `scripts/verify-vendor.sh`; symlinks are not `-type f`, so they can never
     satisfy a manifest entry.

4. **Symlinks**
   - `find` over the resolved tree, pruning top-level `.lake` and `.git`,
     collecting `-type l` entries;
   - an absolute target is reported as `absolute symlink` (the OPS-04 label);
   - a relative target is reported as `relative symlink`;
   - **every** symlink is a failure, because `scripts/fetch-vendor.sh` rejects
     every non-regular archive member. This keeps the directory check and the
     archive check consistent.

A run reports both digest and symlink findings before exiting, so one invocation
shows every publication defect.

## 4. Exit codes and output

| Code | Meaning |
|---|---|
| `0` | manifest canonical, 119/119 digests match, no symlinks |
| `1` | digest mismatch, extra/missing file, malformed or reordered manifest, non-directory/shape failure, or prohibited symlink |
| `2` | usage/configuration error (bad option, missing value, missing manifest) |
| `3` | artifact directory missing (the "no snapshot" case) |

## 5. Reproducibility

- No network, no Git, no `curl`, no package manager.
- No writes inside the repository; scratch files are created with `mktemp -d`
  under `${TMPDIR:-/tmp}` and removed by an `EXIT` trap.
- All ordering uses `LC_ALL=C`; the success/failure lines contain only
  repository-relative or caller-supplied paths (the root-symlink note prints the
  link target, which is environment-specific and only appears on stderr).
- No timestamps, PIDs, hostnames, or random data appear in the result.
- Two consecutive runs on the same tree produced byte-identical combined
  output (`cmp` RC 0), for both the clean fixture and the failing pinned
  snapshot.
- The manifest hash is printed for the release record:
  `aebba40bc5530087c8ce5ca3b0be9929071706d5959e684da5d97f02dce5002c`
  for the current `vendor/VENDOR-SHA256`.

## 7. Scope caveats

- **The OPS-04 symlink was not removed.** `vendor/**` is read-only for this
  lane. The verifier detects and reports it; deleting it is a vendor/repack
  action, after which the snapshot can be archived.
- **This does not close OPS-01.** A verified directory still has to be
  published (checksummed archive + `VENDOR_ARTIFACT_URL`/`SHA256`) or committed
  by the maintainer. The script only makes the candidate publication-ready
  check reproducible.
- **It checks a directory, not an archive.** Use
  `scripts/fetch-vendor.sh --from-tarball <archive> --dry-run` for safe archive
  extraction, then point this script at the extracted tree. Archive-member
  validation remains `fetch-vendor.sh`'s job.
- **The manifest covers bytes only.** File modes, ownership, and mtimes are not
  pinned, matching the existing gate. (`scripts/fetch-vendor.sh` preserves
  executable bits; the canonical tar recipe normalizes ownership and mtime.)
- **The manifest grammar is strict.** A filename containing whitespace would
  not parse in the two-field `sha256sum` format; the current 119-file snapshot
  has no such path.
- **Top-level `.lake`/`.git` are ignored, not required to be absent.** Local
  build caches do not change the digest result. A published source archive
  should still exclude them (as `fetch-vendor.sh` does).
- **No license or provenance judgement.** `docs/LICENSE-DECISION.md` remains
  the decision record for redistributing the `f950806` lineage.
- **No CI change was made.** The patch below is a recommendation for the
  parent/integrator.

Why `--strict-root` in CI: `fetch-vendor.sh` installs a real directory
(`mv` from its staging root), so a symlinked root in CI indicates a damaged or
tampered install and should fail.

Recommended local pre-publication sequence (maintainer, after removing the
stray symlink from the snapshot or building from a clean archive):

```sh
# 1. Safe extraction and manifest check of the archive (no network if local).
./scripts/fetch-vendor.sh --from-tarball /path/to/btc-lean-core.tar.gz --dry-run

# 2. Extract to a candidate directory and run the publication checks.
mkdir -p /tmp/vendor-candidate
tar -C /tmp/vendor-candidate -xf /path/to/btc-lean-core.tar.gz
./scripts/waveh/verify-vendor-artifact.sh --artifact /tmp/vendor-candidate --strict-root
```
